# 专题2:性能与流畅度全面审查(2026-07-28)

## 一、问题定义

用户在流式输出、切换页面、切换主题、切换会话等一切交互中感受到的"流畅度/丝滑感"。
历史背景:重构前大量用户(尤其是**会话多、单会话大**的用户)反馈卡顿严重;后端引入
SQLite 增量更新后缓解,但吐槽仍在。本专题以成熟商业应用的标准,对
**后端数据路径 → 传输层 → 前端渲染管线** 做端到端审查,只找根源、只提终极解法。

审查范围与方法:通读 pc-server(conversations/index、working-set、fts、read-queries、
orchestrator、api/sse、api/handlers/conversations、inference-engine/parts)与 web-ui
(markdown/code-block、chat-message、theme-provider、conversation-sidebar、
conversation-sync、conversation-store/stream),并对热路径做了微基准实测(见附录数据)。

## 二、核心结论(一句话)

**全链路存在同一个模式性根因:"每帧对全量内容重算",成本随内容长度线性增长、随流式
持续时间累积成 O(N²)。** 其中前端 shiki 代码高亮是最大单点(单帧 7-40ms 主线程同步),
传输层全量节点帧是架构性放大器。会话切换/主题切换/列表等路径整体健康,仅有两处
中等规模的扩展性债务。

## 三、根因族总览

| 族 | 优先级 | 根因 | 主要症状 |
|---|---|---|---|
| H-a | **P0** | shiki 每帧全量重分词(主线程同步 7-40ms) | 流式输出含代码块时整个界面卡顿、掉帧 |
| H-b | **P0** | SSE node_update 每帧携带全量节点(O(N²) 字节) | 长回答流式越到后面越卡;前端每帧 parse+GC churn |
| H-c | P1 | 流式期间每 200ms 对整节点做 FTS 重分词+全量落库 | 后端事件循环抖动,长回答时 SSE 发送延迟波动 |
| I | P1 | 会话 SSE 重开即推全量会话快照(无协商) | 大会话切换有可感延迟;LRU 命中也白传几 MB |
| J | P2 | 列表分页端点全表读入 JS 再排序切片 | 数千会话时每次列表刷新 O(总数);invalidate 风暴放大 |

命名承接专题1(A-D 族已结):H = 流式全量重算族(D 族的深水区遗留),I = 大会话快照族
(即此前挂账的 P2 议题),J = 列表扩展性族。

## 四、H 族:流式全量重算管线(P0)

### H-a 前端代码高亮:每帧全量重分词(最大单点)

现场(`web-ui/app/components/markdown/code-block.tsx`):

- `highlightCode(code, lang)` 的缓存键是 `lang + 全文`。流式中代码块每帧都在增长,
  **缓存永不命中**;命中不了就走 `codeToTokens` ——TextMate 语法 + oniguruma WASM,
  **同步跑在主线程渲染路径上**。
- 实测(本机,Bun/JSC;WebView2 的 V8 同量级):tsx 2-12KB 每次全量分词 **37-41ms**,
  python 12KB **36ms**。流式帧率上限 30fps(33ms 一帧)——单是高亮就吃掉超过一整帧,
  主线程饱和,输入、滚动、动画全部跟着卡。**这是"流式输出不丝滑"的最大单点。**
- 次生问题:每帧向 `tokensCache`(上限 200)写入一条"中间状态全文"条目,流式一个
  10KB 代码块产生数百条一次性条目,把真正有用的缓存全部挤掉(缓存污染)。
- 已有的正确设计:Streamdown 块级 memo 保证**只有正在增长的最后一个块**每帧重渲染,
  已完成的代码块不再重算;`MAX_SHIKI_CODE_LENGTH=12000` 封顶;双主题走 CSS 变量,
  切主题不重分词。问题只剩"正在增长的那个代码块"。

终极解法(行级增量分词):

- shiki 暴露每行的 grammar state(`codeToTokensBase` / `getLastGrammarState`)。对流式
  中的代码块,**按行缓存 token + 行末 grammar state**:新 delta 到来时,只对"发生变化
  的最后一行 + 新增行"重新分词,前缀行直接复用。单帧成本从 O(全文) 降到 O(新增行),
  与内容长度彻底解耦——这是 VS Code/编辑器的标准做法,也是唯一"确定性不随长度退化"
  的形态。
- 配套:流式期间不再向全文键缓存写中间状态(行级缓存本身就是缓存);流结束后做一次
  全文精确分词并落全文缓存(修正跨行结构,如未闭合的模板串)。
- 若行级实现风险超预期,退而求其次的过渡方案是"流式期间高亮节流至 ~250ms + 空闲回填,
  完成后全量精确高亮"——但它只稀释成本、不消除 O(N²),不作为终案。

### H-b 传输层:node_update 每帧携带全量节点

现场(`pc-server/api/sse.ts` `broadcastNodeUpdateNow`、`web-ui/app/lib/conversation-sync.ts`):

- 每个 33ms 合并帧把**完整的、累积增长中的 MessageNode** 整体 `JSON.stringify` 推给
  前端;前端整体 `JSON.parse` 后整节点替换进 store。回答长到 300KB 时,每帧 300KB、
  30fps 下 ~9MB/s 穿过 WebView2,总传输量对流长呈 O(N²)。
- 单帧序列化/解析本身不慢(实测 stringify 300KB ≈ 0.15ms,V8 parse ≈ 数 ms),真正的
  代价是:① 前端每帧丢弃整棵旧对象图 → **GC 压力与卡顿尖峰**;② 帧体积随长度膨胀,
  与 H-a 叠加时主线程雪上加霜;③ 多标签页(1.5.0)下同一会话的多个视图共享一条流,
  帧越大放大越狠。
- 代码注释自己也写着:"naive per-chunk broadcasts turn into O(N^2) bytes over SSE"——
  33ms 合并只是限了频率,没有解决字节量级。

终极解法(增量帧协议,成熟流式应用的标准形态):

- 流式热路径改发**追加帧**:`text_delta` / `reasoning_delta`(携带 nodeId、messageId、
  partIndex、追加文本、递增 seq)。前端 store 做字符串追加,单帧成本 O(delta)。
- **关键帧兜底**:结构变化(新 part、工具调用、图片、selectIndex 变化)与流结束时发
  完整 node keyframe;客户端检测 seq 不连续(丢帧/重连)时主动请求 keyframe 重同步。
  行为保真由"关键帧 + seq"保证,数据正确性不依赖增量帧全部到达。
- 前端 `applyNodeUpdate` 家族在 store 中增加 `applyTextDelta`(定位 node→message→part
  后就地追加,保持其余节点引用身份不变——与 D 族细粒度订阅天然契合)。
- 收益:传输字节 O(N²)→O(N);前端每帧 parse+GC 从全节点降到几十字节;后端每帧
  stringify 消失。这是 1.5.0 多标签页共享流的正确地基。

### H-c 后端:流式期间的 FTS 重分词与全量落库

现场(`pc-server/conversations/index.ts` `upsertMessageNode` → `fts.ts` `replaceNodeFts`):

- 每 200ms 脏 flush 时,对整节点执行"删全部 FTS 行 + 全文 trigram 重分词重插"。
  实测 100KB 文本 1.1ms、300KB 3.2ms,5 次/秒——单次不致命,但:① 是纯粹的无用功
  (流式中的半成品文本被反复索引又反复删除);② 同步占用事件循环,与 SSE 发送竞争,
  造成流式延迟抖动;③ 成本 O(全文),对流长累积 O(N²)。
- 同一 flush 里 `JSON.stringify(整节点)` 落库(0.07-0.15ms)——量级可接受,保留
  (200ms 崩溃窗口的持久化保证不能动,用户数据安全优先)。

终极解法:

- **流式期间跳过 FTS 同步**,流结束的 `persistConversation` 全量 reconcile 时一次性
  索引(该路径本就重建 FTS)。搜索语义的代价:正在生成中的内容晚几秒可搜——现状
  本来就有 200ms 滞后注释承认"搜索场景极少针对正在生成的内容",完全可接受。
- 实现要点:给 `upsertMessageNode` 增加"跳过 FTS"的调用形态(或流式 flush 专用入口),
  确保**只有**流式脏 flush 跳过,其他所有调用点(编辑、导入、迁移)语义不变。

## 五、I 族:大会话切换的全量快照(P1,即此前挂账的 P2 议题)

现场(`api/handlers/conversations.ts` stream 端点、前端 `conversation-stream.ts`):

- 每次打开会话 SSE(切换会话、重连、refreshConversation)服务器立即推**整个会话**的
  快照。前端 store 的 20 条 LRU 缓存只省了加载态,不省传输——切回缓存中的大会话
  依然全量重传几 MB。
- 实测 parse 成本不高(3MB ≈ 2ms Bun / 约 10ms V8),主要代价是传输体积、内存峰值、
  以及未来快照更大时的首屏延迟。**几百上千条消息的会话,快照可达 10MB+。**

终极解法(分两步,第二步是终局):

1. **快照协商(低成本,先行)**:前端持有 detail 时,开流带上 `lastUpdateAt`(或快照
   hash);服务器发现未变化 → 只发轻量 `snapshot_meta`(isGenerating 等),命中 LRU 的
   切换零重传。
2. **快照分页(终局,工程量大)**:snapshot 只带最近 N 个节点 + 总数,向上滚动按需
   拉更早分片。涉及 Virtuoso 顶部插入、QuickJump、搜索跳转、分支切换等一整套联动,
   **建议作为独立专题**(与本次 H 族解耦,避免一次改动面过大)。

## 六、J 族:列表端点全表扫描(P2)

现场(`api/handlers/conversations.ts` `conversations/paged`、`read-queries.ts`):

- 每次列表刷新把该助手**全部**会话元数据读入 JS(`listConversationMetas`),再在 JS 里
  filter/sort/slice。注释解释了动机(JS 与 SQLite 的大小写语义差异,保行为等价)。
- 千级会话单次几 ms,可接受;万级(用户画像里存在)每次 10ms+,且 `broadcastList` 的
  invalidate 会让**所有**打开的客户端同时重拉,生成开始/结束、改名、置顶都触发。
- 终极解法:SQL 侧 `WHERE assistant_id = ? [AND title LIKE ?] ORDER BY is_pinned DESC,
  update_at DESC LIMIT ? OFFSET ?`。title 过滤的 Unicode 大小写差异用
  `LOWER(title)`+参数化小写查询近似,或注册自定义 collation 保语义;配
  `idx(assistant_id, is_pinned, update_at)` 索引。属于扩展性储备,不阻塞本专题主线。

## 七、已确认健康的部分(避免误伤)

- SQLite 层:WAL + synchronous=NORMAL + 200ms 节流脏 flush + working set 引用计数,
  设计与实测(upsert 0.02-0.22ms)都健康。**持久化频率与崩溃窗口不动。**
- SSE 基础设施:33ms 合并、背压断连(desiredSize)、6 连接预算纪律(单 events 通道),
  设计正确。
- 前端:Streamdown 块级 memo、插件/components 引用稳定化、双主题 CSS 变量(切主题
  不重分词)、ChatMessage/侧边栏行 memo、Virtuoso 虚拟化、D 族细粒度订阅 + 元数据桥。
- 主题切换:纯 CSS 变量作用域切换,JS 侧零成本;用户主题 CSS 常驻注入、切换零重注入。
  若实测仍不丝滑,瓶颈只会在浏览器全页样式重算(DOM 体积),先观望。
- 页面切换:专题1 已改为即时切换,零中间帧。

## 八、修复优先级与顺序建议

1. **H-a shiki 行级增量分词**(纯前端,收益最大,风险局部可控)
2. **H-c 流式跳过 FTS**(后端小改,立刻消除无用功;注意其余调用点语义不变)
3. **H-b 增量帧协议**(前后端协同的架构性更新,须万分谨慎:seq/关键帧/重同步的行为
   保真清单先行,单测覆盖丢帧、重连、多客户端、工具调用穿插、abort 等场景)
4. **I-1 快照协商**(小改,对大会话用户体感明显)
5. J 与 I-2(快照分页)作为后续独立专题。

数据安全红线(贯穿所有修复):持久化路径(200ms 脏 flush、流结束 reconcile、导入/迁移)
的语义与时序一律不动;H-c 只动 FTS 索引时机,不动数据落库;H-b 只动传输表示,权威
数据仍是服务端内存实例 + 活库。

- 协议:snapshot 只携带最近 SNAPSHOT_NODE_WINDOW(默认 60,可用环境变量覆盖)个节点,
  另带 nodesOffset(窗口首节点绝对下标)与 nodeStamps(全部节点的 wyhash64 内容戳清单,
  O(总数) 但每项仅哈希,远小于序列化传输)。api/snapshot-window.ts 为唯一实现点。
- 分片端点 GET /api/conversations/:id/nodes?before&beforeId&limit:向上翻页取旧节点;
  beforeId 乐观校验——客户端窗口首节点若与服务端该下标不符(结构漂移)返回 409,客户端
  转全量重同步,绝不拼接错位数据。REST 详情端点保持全量(window=Infinity)供兜底。
- 客户端合并(conversation-sync.ts):mergeConversationSnapshot 用 stamp 清单做"可验证
  前缀合并"——新快照到来时,已加载的窗口外旧节点逐个对戳,一致则保留(对象身份不变,
  D 族细粒度订阅不重渲),任何不一致即丢弃回窗口;prependOlderNodes 校验页与本地窗口
  严格衔接(offset/首节点 id 对齐)否则判 stale 重取。
- applyNodeUpdate 窗口感知:载入范围内的节点就地替换并更新戳;窗口下方节点(如切换
  历史分支的 selectIndex 落在旧节点)只更新清单戳不载入内容——下次合并对戳自然失配
  该节点即被authoritative 数据覆盖,内存不涨、正确性不丢。
- UI(conversations.tsx):Virtuoso firstItemIndex=nodesOffset + startReached 触发
  loadOlderConversationNodes,滚到顶自动补页;rangeChanged/QuickJump/焦点滚动全部换算
  局部下标;搜索跳转、分享、导出三处在目标不在窗口内时先 ensureFullConversationDetail
  (拉全量 REST 快照落地)再执行,行为与旧版逐字节一致。
- 一致性底线:所有失配路径(409/stale/戳不符)一律回退到服务端全量快照,客户端永不
  展示拼接错误的数据;协商令牌(I-1)与窗口化正交,snapshot_meta 命中时保留本地已
  加载的更长前缀。
- 单测:snapshot-window.test.ts 5 项 + conversation-sync/store/stream 共 +17 项;冒烟
  runWindowedSnapshotSmoke:8 节点窗口 6 → 首帧 offset=2 且 6 节点、清单长度=8、分片
  端点取回前 2 节点且与全量 REST 逐字节一致、beforeId 错位 → 409。
