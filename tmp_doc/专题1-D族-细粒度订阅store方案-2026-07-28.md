日期:2026-07-28 | 状态:已实施(修复记录见研究报告第九节) | 前置:A/B/C 族修复已完成(见同目录研究报告第八节)

## 〇、决策背景

用户决定 1.5.0 将实现**会话多标签页**(同窗口内多个对话页签、单侧边栏),紧随本专题开工。
因此 D 族不采用保守方案(写侧短路+状态下沉的组件内改造),直接上终极形态:
**按会话 id 索引的细粒度订阅 store**。一次重构同时完成:
- D 族根治:流式增量的重渲染宽度 = 变更语义宽度(侧边栏/顶栏/输入区零波及);
- 多标签页地基:N 个会话同时持有详情状态与订阅生命周期,引用计数共享。

## 二、目标架构

### 新模块 1:`app/stores/conversation-store.ts`(纯状态,zustand,可单测)
```ts
interface ConversationEntry {
  detail: ConversationDto | null; // 最后已知快照(含已应用增量)
  subscribing: boolean;           // SSE 建立中(快照未到)
  error: string | null;           // 致命错误(fatal 4xx)
}
interface ConversationStoreState {
  entries: Record<string, ConversationEntry>;
  // 动作(全部纯状态写,副作用在 stream 模块):
  applySnapshot(conversation: ConversationDto): void;
  applyNodeUpdateEvent(event: ConversationNodeUpdateEventDto): "applied" | "no_detail";
  applyPolledSnapshot(conversation: ConversationDto): boolean; // updateAt 单调守卫,返回是否接受
  setSubscribing(id: string, value: boolean): void;
  setError(id: string, message: string | null): void;
  evict(id: string): void;            // 删除会话/清库
  evictMany(ids: string[]): void;
  touchLru(id: string): void;         // 订阅时提位
}
```
- **entries 即缓存**:取代 detailCache。LRU 语义:无订阅者的 entry 上限 20,超限淘汰最久未用(实现:模块内维护 LRU 顺序表,或用 Map 插入序;被 acquire 的 id 永不淘汰)。
- 每个动作只重建 `entries` 外壳 + 目标 entry:其它 id 的 entry 引用不变 → 订阅其它会话的组件(未来多标签页)零重渲染。
- applyNodeUpdateEvent 内部用现有 `lib/conversation-sync.ts` 的 applyNodeUpdate(身份保持,不动它)。

### 新模块 2:`app/stores/conversation-stream.ts`(命令式,订阅生命周期)
```ts
acquireConversationStream(id: string): () => void  // refCount++,首个引用开 SSE;返回 release
refreshConversation(id: string): void              // 重启流(等价旧 refreshDetail:重连即得全量快照)
onConversationSummaryChange(l: (u: ConversationSummaryUpdate) => void): () => void // 元数据桥
```
- **引用计数**:refCount 0→1 开 SSE,1→0 关闭。StrictMode 双调(acquire→release→acquire)容忍:release 用微延迟(50ms 定时器)真正关闭,期间再 acquire 则取消关闭 —— 避免开发模式双连抖动,生产无行为差异。
- SSE onMessage 语义**逐条照搬** useConversationDetail(snapshot/node_update/error/404/fatal 4xx/setClockOffset/toast);node_update 遇 no_detail → 重启流(取代 refreshNonce 微任务)。
- **10s 轮询兜底**:流打开期间监听 entry.detail?.isGenerating,为真则起 10s interval,GET 快照走 applyPolledSnapshot(单调守卫在 store 动作里,可单测);isGenerating false 或流关闭即停。
- **元数据桥(写侧分类,D 族支柱①)**:applySnapshot/applyNodeUpdateEvent/applyPolledSnapshot 接受后,由 stream 模块比对新旧 detail 的**展示字段**:`title / isPinned / isGenerating` 任一变化才广播 ConversationSummaryUpdate(携最新 createAt/updateAt);纯内容增量(仅 updateAt/messages 变)**不广播** —— 侧边栏从 30Hz 降到"开始/结束/标题生成"各一次。列表排序依据的 updateAt 在广播时携带,足够(流式中列表位次本就不该抖动)。
- 监听器集合模式对齐 services/app-events.ts(故障隔离 try/catch)。

### 消费侧改造
- **消息面板**(colocation,支柱②):自己 `useConversationSubscription(activeId)` + `useConversationEntry(activeId)`,本地派生 selectedNodeMessages/detailLoading/detailError;顶层不再持有 detail 州,相关 props(selectedNodeMessages/isGenerating/conversationAssistantId/conversationTitle)从面板签名中删除。
- **顶层组件**:按上表换窄选择器 —— zustand 按 Object.is 比较选择值,流式期间这些标量不变 → 顶层零重渲染。
- **useConversationList**:effect 注册 `onConversationSummaryChange(updateConversationSummary)`(对齐既有 onAppEvent("invalidate") 模式);hook 的 updateSummary 参数线全部拆除。

## 三、行为保真清单(逐条验收,漏一条都是回归)
1. 切换会话缓存命中零加载态(render 阶段换内容,无旧内容残帧 → 面板订阅+entry 直读天然满足,但**入场动画的 knownIdsRef 播种与滚动播种依赖"首帧即新会话内容"**,面板内那两个 render 阶段播种块原样保留);
2. detailLoading = subscribing && detail===null(缓存命中不进加载态);
3. 404 → 无错误静默;致命 4xx → 错误态;5xx/网络 → sse() 自动重连;
4. event=="error" → toast.error;
5. snapshot/node_update → setClockOffset(serverTime);
6. no_detail 时的 node_update → 重启流拿快照;
7. 10s 轮询仅 isGenerating 期间,updateAt 单调守卫(R7-3 注释迁移);
8. LRU 20 淘汰、删除会话/批删/清库即时驱逐(resetDetail/detailCache.delete 全部对应到 evict);
9. refreshDetail 等价动作(重启流);
10. StrictMode 双挂载不泄漏、不双连(微延迟 release);
11. 元数据桥:标题生成中每帧 title 变化照常广播(打字机标题效果不丢);isGenerating 跳变即时广播(侧边栏生成中圆点)。

## 七、多标签页衔接(1.5.0 后续项目直接引用)
- 本方案交付后,多标签页只需:每个页签挂 useConversationSubscription(tabConversationId) + 面板实例;
- **遗留给多标签页项目的传输问题**:WebView2 同源 HTTP/1.1 仅 6 并发连接,N 页签 = N 条详情 SSE + 1 events,4 个页签即逼近上限 —— 届时需把详情流并入多路复用通道(如 events SharedWorker 通道扩展或单一多路流端点)。本方案的 stream 模块已把传输隔离在 acquire/release 之后,替换传输不触碰任何组件。
