### R1-1(P1)壳 20s 就绪超时 × 首启同步迁移链 = 重数据老用户可能永久无法启动
- 证据:`web-ui/src-tauri/src/lib.rs:38` `SIDECAR_READY_TIMEOUT = 20s`;超时后
  `show_startup_error` + `handle.exit(1)`(lib.rs ~591),而 sidecar 被 Job Object
  (KILL_ON_JOB_CLOSE,lib.rs:289-)连带击杀。服务端侧 `bootstrap()`(含 loadState 全部
  一次性迁移)在 `Bun.serve` 绑定端口/打印 `RIKKAHUB_PORT:` 之前同步执行(server.ts:26)。
- 场景推演:1.4.1→1.5.0 首启要跑 file-dedup(state-load.ts:354-,对 files/ 全部同尺寸组
  做同步 sha256——截图用户几 GB 很常见)+ 抽取旁车迁移 + 路径自愈;pre-1.2.6 直升用户还有
  SQLite 灌库(单事务,全或无)。任何一项超 20s → 壳报"未启动完成,请重试"并杀进程;
  单事务迁移下次从头再来 → **每次启动都超时被杀的死循环**,用户视角=升级后应用彻底打不开。
- 影响面:数据量大的忠实老用户,恰是最不能得罪的人群。
- 修复方向(候选):① 服务端改为"先绑端口打标记,再跑迁移,期间 API 返回 503/前端显示
  迁移进度页";② 壳把固定超时改为"子进程存活即继续等待+可视化等待提示";③ 大迁移分批
  提交(灌库按 N 条一事务,file-dedup 记录进度)。①+② 组合最彻底。

### R1-2(P1)state.json 恢复链新鲜度错序 + recovery/applied 文件永久残留(含全量 API Key)
- 证据:`pc-server/persistence/json-store.ts:92`(八连败后写 `state.json.recovery-<ts>.json`,
  全量 state 含所有供应商 apiKey);`json-store.ts:140-169` 恢复链**无条件**先用任意
  recovery-*.json,再 daily.bak,再 pre-sqlite.bak;`json-store.ts:176-195` 启动清扫只认
  `*.tmp`,recovery-*.json 与用过归档的 `.applied-<ts>` 无任何清理路径。
- 场景推演:某天磁盘满/杀毒锁文件导致一次八连败 → recovery 落盘;之后恢复正常,该文件
  永久残留。数月后 state.json 意外损坏 → 恢复链优先采用**数月前的 recovery**,而昨天的
  daily.bak 明明更新却排在其后 → 用户设置/密钥静默回滚数月,且没有任何提示告知回滚幅度。
- 附带:含明文 API Key 的文件(recovery/applied/daily.bak/pre-*.bak)在磁盘上无限期累积,
  用户拷贝 pc-data 求助/迁移时泄露面变大。
- 修复方向:① 成功落盘后删除所有 recovery-*(它们已过时);② 恢复链把 recovery/daily.bak
  全体候选按 mtime 统一排序取最新;③ .applied-* 与超龄 recovery 纳入启动清扫;
  ④ 恢复成功的 reportError 里写明所用备份的落盘时间,让用户知道回滚到了哪天。
- 补充(用户提问引出,2026-07-26):迁移安全快照缺乏统一保留策略。`pre-sqlite.bak`
  (含全部会话,重用户几十上百 MB)与 `pre-memory-split.bak` 永不过期,救援价值随时间
  贬值却持续占盘,用户翻看 pc-data 会觉得目录被污染。活数据本身无双份(迁移是搬家:
  字段删除/旁车/去重),问题纯在快照生命周期。方向:统一退役规则(迁移标记写入且活库
  健康运行 N 次启动后归档/删除)+ 备份类文件收进 backups/ 子目录用可读命名;另阶段五
  需核对 updates/ 缓存的历代安装包是否清理(潜在同类累积)。

### R1-3(P2)静态服务路径前缀校验无分隔符(经典穿越模式)
- 证据:`pc-server/api/static.ts:22-23` `resolve(staticRoot, requested)` 后仅
  `target.startsWith(staticRoot)`。`staticRoot=/x/build/client` 时 `/x/build/client2/...`
  也通过校验。当前打包布局无同前缀兄弟目录,实际不可利用,但这是审计器一眼红的模式,
  未来目录布局变化即变洞。
- 修复方向:`startsWith(staticRoot + sep)` 或 `!relative(staticRoot, target).startsWith("..")`。

### R1-4(P2)壳启动失败诊断误导 + 死契约标记
- 证据:`pc-server/server.ts:213` 输出 `port_in_use:<port>` 且注释声称"Tauri 壳解析此标记
  显示友好对话框"——`lib.rs` 全文无该字符串;壳对 child_dead **一律**弹"端口被占用"文案
  (lib.rs:173-198),但 sidecar 退出码 3=数据目录被另一实例锁定、1=其他启动失败;
  release 构建(`windows_subsystem="windows"`)下 stderr 不可见,真实原因(实例锁的中文
  提示)用户永远看不到。
- 场景推演:用户双开(或残留孤儿进程持锁)→ 弹"端口被占用,请换端口" → 用户改端口重启
  → 依旧失败 → 无解循环。
- 修复方向:壳区分退出码/解析标记行(如 `RIKKAHUB_FATAL:<code>:<message>`)分诊文案;
  顺手兑现或删除 `port_in_use:` 死契约。

### R1-5(P2,待阶段二定级)流式广播 pendingBroadcasts 条目在异常路径驻留
- 证据:`pc-server/api/sse.ts:20-57`:`flushNodeBroadcast` 只清 timer 不删 Map 条目;
  唯一删除点是 `broadcastNodeUpdate`(终态 flush)→ 若生成异常中断未走到终态 flush,
  条目携带整个 Conversation 对象引用永久驻留(整棵消息树 pin 在内存)。
- 待验证:orchestrator(483/499/627 三处调用)的终态 flush 是否在 finally 中覆盖所有
  退出路径(异常/abort/进程级兜底)。若覆盖则降 P3(仅防御性),阶段二核对。
- 【阶段二收口】已核对:正常/中止/失败路径 finally 均触发终态 flush;仅"流式中删会话/
  导入清库"路径泄漏。**降级 P3**,详见 R2-4。

### R1-6(P3)addLog 每条请求日志触发全量 state 序列化落盘

**B. 有界备份(单代滚动/一次性,设计合理但永不退役)**

- rikka_hub.db.pre-import.bak(每次导入 VACUUM INTO 覆盖,conversations/index.ts:513-525)
  ——单代但体积=整库,重用户数百 MB 永驻。
- state.json.pre-sqlite.bak(1.2.6 一次性化石,含全部会话,数十~数百 MB)——仍被

**C. 无界累积(真正的污染源)**
- state.json.recovery-*.json 及 *.applied-*(R1-2,含全量 API Key,无人清)。
- rikka_hub.db.corrupt-<ts>(损坏隔离取证,conversations/index.ts:39,单个可数百 MB,无人清)。
- memory/*.corrupt-<ts>(memory/index.ts:56,无人清)。
- updates/ 历代安装包:下载的 .exe/.tar.gz 每个版本一份(~80-100MB),extracted-* 只在

- state.json.*.tmp——已有 10 分钟年龄门清扫(1-4),此类无问题。

**修复方向(阶段九细化;安全第一原则)**
1. 任何清理只碰"冗余/可再生/已过期"三类,绝不触碰唯一副本;每次清理留 info 级错误中心痕迹。
2. recovery-*:成功落盘即删(它必然过时);applied-*/corrupt-* 保留最新一份+超龄(如 30 天)清;
   corrupt 大文件可提示用户而非静默删。
3. updates/:启动时删除版本号 ≤ 当前 APP_VERSION 的安装包与对应 extracted-*。
4. 化石快照(pre-sqlite/pre-memory-split):健康门槛退役——活库连续 N 次启动健康(探针通过)
   后,压缩归档到 backups/ 或提示可删;pre-sqlite 退役前需先给恢复链补充替代兜底(如定期
   VACUUM INTO 的活库快照,新鲜度远优于化石)。
5. 目录卫生:全部备份/快照类文件收敛到 pc-data/backups/ 子目录,命名带用途与日期,
   用户一眼可读;根目录只留活数据。
6. 待阶段四核对:files/ 孤儿附件(会话删除后不再被引用的物理文件)是否有 GC——这可能是
   比备份更大的隐性占用。

### R2-1(P1)truncateIndex 在消息树缩短后不钳制 → 上下文静默全空【已修复:随 R2-7 整体移除】
- 证据:编码侧 `inference-engine/conversation-encoding.ts:101-103`
  `applyTruncateIndex = nodes.slice(truncateIndex)`,无上界钳制;而全部缩树路径都不调整
  truncateIndex:regenerate(handlers/conversations.ts:267 及 truncateConversationForRegenerate,
  conversations/index.ts:600-616)、编辑消息(handlers:348 slice)、删除消息(handlers:309-315
  filter)。钳制只存在于 truncate 端点自身(nextTruncateIndex)。
- 场景推演:10 节点会话,用户在末尾"清除上下文"(truncateIndex=10);之后编辑第 3 节点的
  消息(树截到 4 节点)→ 自动触发重新生成 → slice(10)=[] → **模型只收到 system prompt,
  连刚编辑的用户消息都不在上下文里**,回复必然文不对题且无任何报错;前端分割线因索引
  越界不渲染,用户无从发现和撤销。fork 继承越界 truncateIndex(handlers:452 spread),同病。
- 影响面:用过"清除上下文"再编辑/回退/删除消息的任何用户;静默错误,难以自查。
- 修复方向:① 所有缩树路径统一钳制 `truncateIndex = Math.min(truncateIndex, messages.length)`
  (或 ≤0 归 -1);② 编码侧与前端分割线各加防御性钳制;③ 与 R2-7 一并做产品决策。
- **处置(2026-07-27)**:用户决策跟随安卓删除整个机制(见 R2-7),truncateIndex 全链路
  移除后本缺陷不复存在,无需钳制。

### R2-2(P2)fire-and-forget 续体在 checkout 释放后写会话(工作集双实例风险窗口)
- 证据:`api/handlers/conversations.ts` 子路由块 try/finally 在返回时 release(498-500),
  但 messages POST(146-153)与 translate(381-424)的 `void (async ...)` 续体在 release
  **之后**继续 await(OCR/翻译,可长于 60s)再写 conversation 并调 generateAnswer。
- 场景推演:发消息后立即切走会话(SSE 关) → 实例 refs=0、非生成中、无脏标记 → 60s 后被
  sweep 清出;慢 OCR 完成后续体写的是**孤儿对象**,generateAnswer 的 checkout 从活库装出
  第二实例进注册表 → 流式内容写进孤儿,flushConvDirty/completeConversationGeneration 却
  persist 注册表里的陈旧实例 → **屏上看得到回答,重启后消失**(UI 与磁盘分叉)。
- 这正是 working-set 声称的核心不变式("持有实例期间 checkout 必返回同一实例")被
  fire-and-forget 模式绕过——防护应是结构性的,不该依赖"OCR 一般不超过 60s"。
- 修复方向:续体自身 checkout/release 包住全生命周期;或 generateAnswer 入口校验
  checkout 返回实例 === 传入实例,不一致时以注册表实例为准重放。

### R2-3(P2)OCR 窗口内连发两条消息 → 并发生成写同一节点
- 证据:messages POST 的 generateAnswer 在 OCR 续体里异步触发(handlers:146-153)。
  handler 同步段的 abort 守卫(132-133)只能中止**已登记**的生成;A、B 两条消息在 OCR
  期间相继进入时,B 入场时 A 的 generateAnswer 尚未 set generating,无可中止。
- 场景推演(需 OCR 开启+偏慢):两续体先后调 generateAnswer 并发跑;A 见末节点为 userB
  → 新建 assistant 节点;B 见末节点为 A 的空 ASSISTANT 占位 → `ensureAssistantGenerationNode`
  复用之 → **两路流式交错写同一 message,parts 交叉污染**;generating Map 后写覆盖前写,
  A 的 controller 失去登记、无人能停。
- 修复方向:generateAnswer 入口对 generating.has(id) 自带"先 abort 旧流"守卫(把 2-1
  的端点级纪律下沉为编排器不变式);或按会话串行化生成队列。

### R2-4(P3)R1-5 定级收口:pendingBroadcasts 仅在"流式中删会话/导入清库"路径泄漏
- orchestrator finally(623-628)在会话已删时提前 return,跳过终态 broadcastNodeUpdate
  (唯一的条目删除点)→ 该条目连同已删会话整树永久驻留。正常完成/中止/失败路径都会
  清理。频率低、有界(每次删流式中会话泄 1 条),降级 P3。
- 修复方向:deleteConversationsById/clearWorkingSet 时按 convId 前缀清 pendingBroadcasts;
  或 flushNodeBroadcast 在非生成期直接删条目。

### R2-5(P3)会话操作端点残留大量无效 saveState()
- pin/title/truncate/move/system-prompt/stop/regenerate/fork/tool-approval/删除等每个端点
  都调 `saveState()`(全量序列化 state.json),但 state.json 已不含会话数据——除
  bumpAnalyticsMsgCount(计数)外均为纯浪费 IO(与 R1-6 同根:遗留调用未随 DB-first 清理)。
- 修复方向:逐点删除或收敛到真正改 state 的位置;与 R1-6 一并处理。

### R2-6(P3)删除会话不关闭其已打开的详情 SSE 连接
- `helpers.ts:35` 仅 `conversationClients.delete(id)` 摘掉集合,不对 controller 调 close;
  已打开的详情流从此只收心跳,靠前端收到 invalidate 后自行切走。连接悬挂有限但不体面。

### R2-7(P3,产品/互操作)truncateIndex 机制与最新安卓已分叉【已修复:跟随安卓删除】
- 决定性证据:安卓提交 `1f572a80`(2026-03-03)"refactor(chat): 移除截断上下文功能——
  删除 truncateIndex 相关的全部逻辑与 UI,包括截断分隔线、'清空上下文'菜单项、数据库
  字段及迁移,并将数据库升级至版本 17"。这是作者有意识的产品决策,非重构遗漏;当前
  安卓字符串资源已无任何"清除/清空上下文"入口。
- 安卓的职能替代(非同等机制):①**压缩上下文** `ChatService.compressConversation`
  ——手动触发,压缩模型把旧消息总结成摘要、保留最近 N 条(可输入,默认 32),**破坏性**
  (UI 警告"压缩上下文将重置当前对话中的所有消息"),且作者持续迭代中(分 chunk、保留
  最新消息配置);②**助手级 contextMessageSize** 滚动窗口——`GenerationHandler.kt:388`
  `limitContext` 只发最近 N 条,并新增截断/提示词缓存警告文案。
  即安卓用"破坏性压缩 + 滚动窗口"替代了"非破坏性插标记";轻量清除方式无继任者。
- 互操作现状:PC→APP 时 `truncate_index` 被安卓直接丢弃(列不存在),不损数据;
  APP→PC 无此字段输入。往返(PC→APP→PC)后用户设置的清除点**静默永久消失**——
  功能性丢失,非数据损坏。
- 修复方向:产品决策——保留为 PC 特性 or 跟随安卓删除。
- **处置(2026-07-27,用户决策:跟随安卓)**:两个替代机制 PC 早已具备且与安卓同构
  (压缩对话历史 `conversations/auxiliary.ts compressConversation`,算法逐行同源:
  keepRecent 默认 32、256 条分 chunk、摘要作 USER 消息+保留尾部、破坏性替换;
  助手级 contextMessageSize 于 `conversation-encoding.ts` 切片)。执行内容:

  nextTruncateIndex 及 compress 的 truncateIndex=0 写入;② 活库一次性迁移
  `dropTruncateIndexColumnIfPresent`(PRAGMA 探测 + ALTER TABLE DROP COLUMN,幂等,
  失败仅告警不阻断,对齐安卓 Migration_16_17);③ 备份对齐:pcdump 导出 schema 去列,
  导入侧显式列名 SELECT 天然兼容带列的老 dump(已演练验证);安卓导入侧删字段填充;
  ④ 前端删分割线组件、"清除上下文"菜单项、相关 i18n 词条与类型字段;⑤ 测试:删
  truncate-index/truncate-toggle 两个死测试,修 6 个测试与 verify-persistence-fixes
  场景脚本(老 state.json 种子保留 truncateIndex 字段模拟老格式输入,断言改为字段
  已被移除)。老库迁移演练(带列库→打开→列删数据无损→幂等)与老 dump 导入演练全 PASS,
