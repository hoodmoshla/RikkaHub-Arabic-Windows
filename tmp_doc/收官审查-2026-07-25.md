# 重构收官系统性审查报告(2026-07-25)

审查方式:主线亲自核验 + 四路并行深审(A 后端并发与数据完整性 / B 跨端备份与部署 / C 推理引擎与横切面 / D 前端架构与未来路线)。所有 P0 结论均由主线逐行复核代码证据后确认(非仅代理转述)。审查范围:pc-server/ 全域 + web-ui/ + Dockerfile/CI + Android schema 交叉核对。

未来路线视角:① 多标签页 → ② 前端 UI/UX 重设计 → ③ 大文件流式上传+逐页解析 → ④ Agent 化(工作区)。

**总判断:本次重构的架构骨架(DB-first + working set + 统一工具循环 + 类型单源)方向正确、地基扎实,但收官状态尚不可发版——存在 3 个已复核确认的发版级阻断问题(2 个数据丢失/损坏 + 1 个部署形态构建断裂),另有一批影响未来路线的架构短板。必须先清 P0 再发版。**

## 一、发版阻断(P0,主线已逐行复核确认)

### P0-1 【数据丢失·最高危】纯 PC 用户备份→恢复自己的备份 = 静默清空全部会话

**完整故障链(四环各自"有理由",串起来是灾难):**
1. `backup/export.ts` `backupPayloadMetadataOnly` 明确不再把 conversations 写进 pc-backup.json(注释:"exported as rikka_hub.db now",为避免大历史 OOM)。
2. `generateRikkaHubDb`(export.ts:~200)硬依赖 `dataDir/rikka_hub_cached.db` 模板——该模板**只有导入过一次安卓备份才存在**。纯 PC 用户(从没用过安卓端)导出的 zip **既无 conversations 内联、也无 rikka_hub.db**,仅 `reportError` 记一条 warn。
3. 恢复路径 `backup/import.ts:135` `setState(normalizeState(...))`,`state-load.ts` 的 `normalizeState` 把缺失的 conversations **归一化为 `[]`**;无 rikka_hub.db 可读(import.ts:153-161,读失败仅 console.warn)。
4. `finalizeConversationImport`(import.ts:706)判 `Array.isArray(state.conversations)` —— `[]` 也是数组 → 真 → `resetConversationsDbTo([])` → `DELETE FROM pc_conversation` **全表清空**。且 `data.ts` 向 UI 报 `dbReadError: null` 硬编码 → 用户看到"导入成功"。

**同型旁路:** `applyBackupPayload`(import.ts:56-92)的纯 JSON 导入路径同样无守卫。对照:settings-only Android zip 路径有专门守卫(import.ts:417 `delete state.conversations`,注释标了 P0),PC 恢复/JSON 路径没有等价保护。

**影响面:** 纯 PC 用户(占比可能很高)拿自己的备份做恢复即触发;WebDAV/S3 下载截断、zip 内 db 页损坏也触发。这是"用户用自己的备份反而清空自己数据"。

**修复方向:** ① `resetConversationsDbTo` 前对活库做导入前快照(`db.serialize()` 落 `rikka_hub.db.pre-import-<ts>`);② 新格式 zip 若 pc-backup.json 无 conversations 且 rikka_hub.db 缺失/读失败 → 降级 settings-only 语义(`delete state.conversations`,不碰活库);③ 真实 dbReadError 上报 UI;④ 恢复前 UI 明示"该备份不含会话,继续将清空本机 N 条会话";⑤ 根治:随包内置与 APP 当前 Room schema 对齐的空模板,或让 PC→PC 用独立 dump 承载会话,与安卓模板解耦(见 P1-B3)。

### P0-2 【流式体验回归 + 崩溃丢数据】纯文本流式既不增量广播、也不增量落库

**证据(主线复核):** provider 层 `addStreamText/appendReasoningDelta/addStreamImage`(inference-engine/parts.ts)带 sink → 只 emit 事件;orchestrator `applyEvent`(orchestrator.ts:518-559)的 sink 处理里,text_delta/reasoning_delta/image_delta **只改内存 parts,不调 `touchStream`**;唯有三个 tool 事件(540/547/554)调了 `touchStream`。`touchStream`(sse.ts:185-198)才是"标脏 + 200ms 节流落库 + 33ms 节流广播"的唯一入口。

**git 考古:** 5.3g(ab818b4)把 applyEvent 的文本写入从 server.ts 本地版(末尾含 touchStream)换成 parts.ts 版(不含),提交号称"纯搬迁行为不变",实为回归。

**为何单测/smoke 没抓到:** request-chain smoke(scripts/request-chain-smoke.ts:924)场景**强制调用工具**("请调用本地时间工具"),node_update 断言(935)由 tool 路径的 touchStream 满足——**纯文本无工具的流式路径零覆盖**。

**影响:** 无工具的普通对话(绝大多数流量)从首 token 到结束,前端收不到任何 node_update,用户盯着占位符直到 finalize 一次性砸出全文("卡住然后整段弹出"),正是当年"全量刷新→SQLite 增量"要根治的病症被变相复活;且流式期间不标脏,**中途崩溃/断电丢整段回答**(finalize 前无任何落库)。

**修复方向:** applyEvent 的 text/reasoning/image case 后补 `touchStream(streamHooks)`(与 tool case 对齐);给 smoke 加"纯文本对话流式期间必收 ≥2 帧 node_update"断言防再回归。

### P0-3 【部署形态断裂】Docker 镜像构建即失败

**证据(主线复核):** `Dockerfile:51` 仅 `COPY pc-server/server.ts ./`,`:58` `bun build --compile server.ts`;但 server.ts 现 import 37 个本地模块(重构模块化产物),这些文件不在镜像层 → bun 解析 import 即失败,镜像构不出。`docker-publish.yml` 每次 push 触发 → CI 红灯。README 公开推荐 Docker 部署。

**修复方向:** `COPY pc-server/ ./`(bun install 已重建 node_modules,必要时 .dockerignore 排除);build-linux.yml 的完整 checkout 是对的可参照。

## 二、商业级功能缺口与一致性缝隙(P1)

**后端并发(A):**
- **A-P1 删除会话与长操作竞态:** `persistConversation`(index.ts:268-287,INSERT OR REPLACE)无存在性守卫;translate/compress/OCR 续体每 delta 直调它。标签 A 删会话、标签 B 翻译流仍在跑 → 每 delta 把整棵树写回,已删会话在 DB 复活。修:调用侧加与 flushConvDirty 同款"仍在注册表/DB"守卫。
- **A-P0候选 并发生成互覆(主线认定 P0 级,列此因触发需特定时序):** `generateAnswer`(orchestrator.ts:455)`generating.set` 无条件覆盖、不 abort 旧 controller;OCR 窗口内快速连发两条,或多标签同会话同时发,两路 provider 交错写同一 message → 内容损坏 + 幽灵流。修:入口检测 `generating.has(id)` 先 abort,或按会话串行。
- **A-P0候选 fire-and-forget 续体逃逸 checkout 窗口:** 三处 `void (async()=>{})()` 续体在 handler release 后长 await 改会话,refs=0;SSE 已关 + 超 60s 宽限被 sweep → `generateAnswer` 的 `checkoutConversation` 返回值不校验同一性,装出第二实例,写入落游离对象,flush 跳过 → 整条回答刷新后消失。修:checkout 断言 `=== conversation`;续体自持 checkout/release。
- **A-P1 SSE 裸 enqueue 无 try/catch(sse.ts:114/131/141/159):** 死连接抛错可打断生成收尾,多标签放大命中率。修:enqueue 全包裹,失败摘除 controller。
- **A-P1 长消息流式 O(N²) 字节:** 每帧携带完整增长节点,10 万字符流 ≈ 270MB/客户端,多标签再乘。修:改"文本增量帧 + 周期快照帧"混合协议。
- **A-P1 translate/compress 每 delta 全树 reconcile + 全量快照广播;列表/搜索每请求全量捞取 + pc_conversation 无二级索引**(1 万会话可接受,10 万退化)。

**跨端备份/部署(B):**
- **B-P1 PC→PC 丢字段:** 导出 INSERT 列不含 `custom_system_prompt`(export.ts:288),导入 `truncateIndex:0` 硬编码(应 -1)→ 逐会话系统提示词恢复后全丢。
- **B-P1 模板 schema 版本漂移无护栏:** 老模板生成的库导回新 APP 靠 Room 迁移链兜底(要求 APP 永不删旧迁移);模板比手机 APP 新则 Room 无降级路径,恢复即崩。PC 端零提示。
- **B-P1 大附件导出必败:** zip 压缩 spawnSync `timeout:120_000`(export.ts:416/424),自家宣称支持 4-10GB 备份,10GB 压缩超 2 分钟被杀。
- **B-P1 Linux 裸机依赖系统 zip/unzip**,无预检;Docker 已自带(处理正确)。

**推理引擎/Agent 准备(C,准备度 6.5/10):**
- **C-P0候选 自定义搜索脚本零沙箱(search/index.ts:91):** AsyncFunction 同 realm 执行,可读 state.json 全部 API key。单机自用可接受,一旦社区"分享搜索配置"即社工 RCE。修:短期 UI 强告警,中期 Worker 隔离。
- **C-P0候选 上传全量入内存(files.ts:16 formData + 64GB body 上限):** 8GB 文件峰值 8-16GB 内存 → 单进程 OOM 全会话齐死。修:立即把 maxRequestBodySize 降到 512MB 级。
- **C-P1 Claude thinking signature 跨请求丢失:** message-builder.ts:245-262 重建 assistant 轮无 signature block → thinking 开启 + 审批暂停/进程重启后续传,Anthropic 400。Agent 化长工具链必然穿插审批,现在就是 bug。修:signature 作 opaque 持久化进 reasoning part。
- **C-P1 工具循环每轮全量重发历史,无上下文管理层:** 50 步链 O(N²) token;骨架无裁剪/摘要/预算 hook,超限直接抛错无软着陆。Agent 化第一堵墙。
- **C-P1 文件解析架构与"大文件流式+逐页"冲突:** extractedText 全文内联进 state.json(每次节流保存整体重写),50MB txt 拖垮 SSE 流畅性;上传即全文提取即入 state 模型基本要推倒(解析器本体 mupdf 逐页可留,存储/注入层重做)。

**前端/未来路线(D):**
- **D-P0候选 会话详情三写入源无版本守卫:** 初始 GET / SSE / 10s 轮询均无条件 setDetail,在途轮询响应可覆盖已完成消息成半截 + 重新转圈 10s(routes/conversations.tsx:442-537,conversation-sync.ts 无 seq 比较)。修:加单调 revision,统一 setDetailIfNewer。列表侧已有 epoch 防御(use-conversation-list.ts)可照抄。
- **D-P0候选 编辑草稿元数据泄漏:** 编辑中途切会话再回来走普通提交,内部编辑标记随新消息入库(普通提交路径缺 stripEditDraftMetadata)。
- **D-P0候选 聊天附件上传硬吃 ky 30s 超时**(lib/upload.ts:207 未传 timeout,images.tsx 已修但主聊天漏)。
- **D-P0候选 模型错误正则误报:** chat-message.tsx:106 对助手正文匹配 `请求失败|404|500|timeout...`,编程助手讨论"404 与 500 区别"即误显示硬编码中文"打开模型设置"。
- **D-P1 多标签当场死亡点:** 单 SPA 已开 5 条 SSE,HTTP/1.1 每源 6 连接上限 → 第二标签 5 条 SSE 建不起来,fetch 静默排队。修:SSE 单连接多路复用(纯数据层改动,今天就该做——长请求已在阻塞所有 REST)。
- **D-P1 全局单例 store 无跨标签同步**(无 BroadcastChannel);Tauri 壳单窗口硬编码(capabilities 仅 main)。
- **D-P1 conversations.tsx 2026 行正成为下一个 settings.tsx 巨型单体**,且 memo 隔离契约已被击穿(不稳定 props 每帧新建 → 流式 30fps 全可见消息行重渲染);数据 hook 定义在路由文件里,重设计 UI 必须连带搬运。
- **D-P1 上传管线一次性 FormData,无进度/分块/单布尔互斥**,与路线③冲突。
- **D-P1 类型单源豁口:** Settings 383 行仍是前端手写本地定义,与后端零 import 关系,四条路线都要动它。

## 四、结论与建议路线

**架构判断(激进版):** DB-first + working set 的单实例注册表 + 引用计数 + 四条件清扫,方向对、地基对,server-authoritative + SSE 快照补偿的数据面甚至为多标签准备得意外地好——这是重构的真红利。但收官状态暴露两条系统性裂缝:

1. **"持有纪律"靠注释约定而非机制**:A 组的并发互覆、续体逃逸、checkout 不校验同一性、persistConversation 不查存在性,是同一根因的四个切面。建议给 working set 加"代际号 + 同一性断言",把违规从静默数据分叉变成显式报错。
2. **"纯搬迁行为不变"的承诺已失守过至少一次**(P0-2 流式回归),而单测全绿(测的是模块内不变量,测不到跨层链路)。补跨层冒烟(流式必收多帧、备份 unhappy path)比再多一轮人工审查可靠。

**发版前必须清:** P0-1(备份恢复守卫 + 快照)、P0-2(流式 touchStream + 冒烟)、P0-3(Dockerfile);强烈建议连带清 A/D 的几个 P0 候选(并发互覆、续体逃逸、上传超时、错误正则、详情版本守卫)与 C 的两个一行改动(上传体积上限、搜索脚本 UI 告警)。

**未来路线次序建议:**
- **SSE 单连接多路复用**提前单独做(纯数据层,今天就在让长请求阻塞 REST,对现版本用户立即有收益,且是多标签地基)。
- **UI/UX 重设计放在多标签之前**,但带着多标签地基一起做——两者的前置工作(拆 conversations.tsx、修 memo 契约、hook/handler 出路由文件、单例状态出组件)是同一批改动;先重设计等于免费完成多标签 ~60% 地基。
- **大文件流式上传**要先做存储层分家(extractedText 出 state.json、分页产物旁路存储)再动传输层。
- **Agent 化**首件事是给工具循环骨架加上下文管理策略接口(裁剪/摘要/预算),这是动契约的改动,晚加代价大;并先修 C-P1 thinking signature 持久化。

**准备度打分:** 多标签 3/10、UI/UX 重设计 6/10、大文件流式 4/10、Agent 化 6.5/10。地基合格,但每条路线都有明确前置债务,且发版前的 3 个 P0 是硬门槛。
