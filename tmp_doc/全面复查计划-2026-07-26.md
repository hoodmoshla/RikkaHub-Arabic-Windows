## 工作协议(每次 compact 后先读本节)

1. **恢复流程**:compact 后先读本文件 + `全面复查发现-2026-07-26.md`,从下方"阶段清单"
   第一个未勾选阶段继续。不要重查已勾选阶段。
2. **只查不改**:本轮是诊断,发现的问题一律记录进发现文档,**不动代码**
   (修复在阶段九统一规划成批次,经用户确认后执行)。
3. **亲自读码**:不用子 agent。大文件用临时脚本分段读(bun -e 行号打印),复杂查询写
   `scripts/tmp-*.ts`(用完即删)。注意 `rg` 不要带 `-r`(那是替换标志)。
   **工具坑(阶段一实证)**:IDE 的 Read 工具在本仓库路径下会返回陈旧内容(bootstrap.ts
   读出了旧版本,漏掉实例锁调用),读文件一律用 `bun -e` 行号打印,勿信 Read 结果。
4. **发现记录格式**:写入发现文档对应阶段章节,编号 `R<阶段>-<序号>`,标注严重度:
   - P0 = 数据丢失/崩溃/安全洞,商业应用不可接受
   - P1 = 功能错误/明显卡顿/互操作破坏,用户可感知
   - P2 = 架构缺陷/可维护性差/边界未处理,迟早出事
   - P3 = 代码异味/冗余/不一致,顺手清理级
   每条含:证据(文件:行)、场景推演(corner case 怎么触发)、影响面、修复方向草案。
5. **每阶段收尾**:更新本文件勾选状态 + 在发现文档写该阶段小结(条数/严重度分布/
   最重要的 1-3 条),然后向用户汇报并等待 compact。

## 背景速览(代替重构方案文档的最小上下文)

- 起源:安卓 APP RikkaHub(第三方作者,源码在 /Rikkahub-Android)的桌面端重制,
  两端数据可经备份 zip 互迁(PC 单方面适配,APP 作者不配合,**互操作契约脆弱需重点审**)。
- 形态:Bun + TypeScript 服务端(pc-server,编译单 exe) + React Router v7 SPA(web-ui)
  + Tauri(Rust)壳,NSIS 安装包;另支持 Linux 二进制与 Docker(纯浏览器访问)。
- 历史顽疾(用户口述):HTTP/1.1 六连接饥饿(已两轮治理:events 单通道+SharedWorker);
  流式全量刷新(已改 SQLite 增量);架构臃肿冗余,维护困难 → 触发本次重做级重构。
- 重构已完成的大事(git log 可考):bootstrap 显式化、会话迁出 state.json 进 SQLite
  (DB-first + working-set 单实例注册表)、api/handlers 拆分、错误中心、事件通道合一、
  会话详情内存缓存、truncateIndex 对齐安卓、附件旁车抽取等。
- 未来路线(审架构时用此视角衡量可拓展性):多标签页 → 前端 UI/UX 重设计 →
  大文件流式上传+逐页解析 → 工作区/Agent 化。
  - 用户决策(2026-07-27):本地 stdio MCP(应用拉起本地 MCP 子进程)划入"工作区/Agent 化"
    阶段一并实现,本轮重构不动;当前仅支持 streamable_http/sse 两种 HTTP 传输,
    与安卓对齐。用户可用 mcp-proxy 等桥接工具自行变通。
- 版本:当前 1.5.0(测试构建阶段,用户正实测);老用户从 ≤1.4.1 升级的迁移路径必须无损。

## 附:各阶段通用检查清单

每个模块过一遍:
1. **职责边界**:单一职责?跨层伸手(如 handler 直摸 DB/全局可变状态)?循环依赖?
2. **错误路径**:每个 catch 是否有意义(上报/降级/注释意图)?错误是否到达用户?
3. **并发/竞态**:共享可变状态的写点;async 空窗期的状态假设;定时器/事件的清理。
4. **资源生命周期**:文件句柄/进程/连接/监听器的成对开关;泄漏点。
5. **数据契约**:DTO 双端一致?持久化格式版本化?向后兼容?
6. **规模退化**:数据量 ×100 时哪里先崩(全量遍历/全量序列化/无分页)。
7. **冗余与死代码**:重复实现、无引用导出、过时注释、临时脚本残留。
8. **测试覆盖**:关键路径有无回归锚点;测试是否测行为而非实现细节。
