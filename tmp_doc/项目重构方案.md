# Rikkahub Desktop 项目重构方案

> 版本：v1.4.1 → 架构重构（修复式渐进模块化）
> 撰写对象：给上下文压缩后半失忆的自己和协作子 Agent 阅读
> 核心纪律：不改数据契约、不改备份格式、不改迁移常量；每步可回滚；每步测试必须绿

---

## 1. 项目背景与前因后果

### 1.1 这是什么产品

Rikkahub Desktop 是一款本地优先的 AI Chatbot 桌面客户端，支持 Windows 便携版、Linux 二进制、Docker 三种部署方式。核心能力是让用户接入自定义 LLM API（OpenAI / Claude / Google 等）进行日常对话，并支持搜索引擎、MCP、Skill、世界书、Lorebook、文件上传、图片生成、TTS/ASR、记忆系统、数据备份迁移等扩展功能。

未来有向 Agent 方向演进的可能（让模型执行动作、调用工具、访问外部服务）。

### 1.2 当前代码现状（实测数据）

| 项目 | 数值 | 说明 |
|---|---|---|
| `pc-server/server.ts` | **18,246 行 / 792 KB** | 整个后端在一个文件里 |
| 顶层函数 | **520 个** | 全部平铺在同一模块作用域 |
| 顶层类型 | **51 个** | 内联在 server.ts 中 |
| 全局 `state` 引用 | **~300 处** | 任何函数都可以直接读写 |
| 路由分支 | **107 个** | 全部内联在 `routeApi()` 一个函数里 |
| `tsc --noEmit` 错误 | **72 个**（以实际 tsconfig 为准） | 后端无 tsconfig，从未类型检查 |
| 前端 `routes/settings.tsx` | **9,407 行** | 前端对应的巨型单体 |
| 后端测试 | 1 个端到端 smoke（2,152 行） | 无单元测试 |
| 前端测试 | 3 个 lib 纯函数测试 | 组件/数据流零测试 |

### 1.3 用户的批评（也是本次重构的起点）

> "一个 TypeScript 文件里面怎么塞了快 2w 行代码？连 LSP 检查都过不了，变量赋值、提示词、控件、配置文件、样式、TS 全在一个文件里面。"

这个批评指向两个层面：

1. **后端 `server.ts` 18k+ 行**：持久化、Provider、SSE、工具、搜索、备份、TTS/ASR、文档解析、代理、路由全塞在一起。
2. **前端 `routes/settings.tsx` 9k+ 行**：设置页把所有配置表单、对话框、本地状态全塞在一个路由文件里。

### 1.4 根因性问题

1. **没有架构，只有实现**：没有模块边界、没有依赖方向、没有接口契约。
2. **全局可变状态**：`let state` 被 ~300 处直接读写，数据流不可追踪。
3. **核心函数是事务脚本**：`generateAnswer()` 同时做生成、持久化、SSE 广播、改状态。
4. **后端无类型检查**：72 个 tsc 错误，全靠运行时踩雷。
5. **循环依赖**：`tools.executeToolCall()` 调用 `generateAnswer()`，后者又调用 `tools`。
6. **测试覆盖极差**：只有一个端到端 smoke，无法做单元级回归。
7. **安全短板**：默认监听 `0.0.0.0`、无鉴权、`eval_javascript` 工具实际是 `new Function()`。

### 1.5 为什么必须现在做

- 用户量已经很大，每次更新都是全局回归风险。
- 单文件已经让 LSP 和类型检查失效，开发效率急剧下降。
- 未来做 Agent 能力时，事务脚本式的 `generateAnswer()` 会成为最大瓶颈。
- 不重构的话，新增任何一个功能都会继续加重 `server.ts`。

## 2. 重构目标与不可触碰的约束

### 2.1 目标

1. **物理拆分**：把 `server.ts` 从 18k 行拆成多个职责单一的模块，最终 `server.ts` 只剩装配逻辑。
2. **依赖方向清晰**：`foundation → persistence → domain → api → app`，禁止循环依赖。
3. **类型安全**：后端接入 `tsconfig.json`，清零 tsc 错误，CI 强制跑 typecheck。
4. **可测试**：每个模块有明确接口，支持单元测试；保留并强化 smoke 作为回归基线。
5. **性能不降级**：流式热路径保持高效，拆分不引入额外 I/O 或阻塞。
6. **安全补强**：绑 `127.0.0.1`、鉴权/Origin 校验、移除/替换 `eval_javascript`。

### 2.2 绝对约束（碰了会伤害老用户）

以下这些东西**只准原样搬迁，不准修改逻辑**。

| 约束 | 说明 | 风险 |
|---|---|---|
| `state.json` 字段与格式 | 老用户启动时靠它加载状态 | 改错导致启动失败或数据丢失 |
| `rikka_hub.db` 表结构 | 会话 SQLite 活库 | 改 schema 导致老用户会话读不出 |
| `memory/` 目录结构 | 1.3.2 记忆系统拆分后的新家园 | 改结构导致记忆丢失 |
| 迁移常量 | `conversations-sqlite-1.2.6`、`memory-file-split-1.3.2` | 改了会让升级用户重复迁移 |
| 备份 zip 结构 | PC 备份的目录布局 | 改了老备份无法导入 |
| Android 互导契约 | FTS5 影子表排除、枚举过滤、MemoryEntity、avatar 转换、settings 七层合并 | 改了导致 Android 导入崩溃 |
| Provider 消息格式 | OpenAI/Claude/Google 的请求体/响应体解析 | 改了导致某些模型不可用 |
| 文件命名规则 | `files/` 下 `<id>.<ext>` | 改了导致文件路径失效 |
| 默认配置语义 | `defaultSettings()` / `defaultState()` 的字段默认值 | 改了可能导致老用户配置被覆盖 |
| 全局初始化顺序 | loadState → installProxy → Bun.serve | 改了可能导致启动失败或代理失效 |

**纪律**：任何改动如果会影响以上契约，必须单独评审，并跑备份往返测试。

## 3. 核心决策：修复（渐进式重构），不要重做

### 3.1 为什么不做重做

| 维度 | 重做 | 修复（渐进模块化） |
|---|---|---|
| 实战边界修复 | ❌ 数百个边界需重新踩雷 | ✅ 原样保留 |
| 跨端备份契约 | ❌ 无对照物，极易回归 | ✅ 契约冻结，测试护航 |
| 单 exe 发布 | ❌ 需重建整条链路 | ✅ Bun compile 支持多文件 |
| Linux/Docker | ❌ 需重建 | ✅ 构建脚本调整即可 |
| 风险粒度 | 一个巨型高风险切换 | 数十个可回滚小 commit |
| 见效速度 | 数月无可用产物 | 第一步当天见效 |
| 老用户迁移 | ❌ 数据格式可能变 | ✅ 无感迁移 |

### 3.2 核心论点

> 项目的问题不是「逻辑烂」，而是「没有边界的好逻辑」。代码里沉淀了大量实战边界修复与跨端契约，这些是核心资产。重做会把这些资产一起丢弃；渐进式重构是在保持行为不变的前提下给好逻辑建立边界。

## 4. 架构愿景（源码验证后的模块划分）

### 4.1 最终目录结构

```
pc-server/
├── foundation/                  # 基础设施：不依赖任何业务
│   ├── types.ts                 # 共享类型（Settings 后续需拆分）
│   ├── utils.ts                 # 纯工具函数
│   ├── platform.ts              # Windows/Linux/容器判断
│   ├── paths.ts                 # 路径常量
│   └── net.ts                   # 代理 + fetch 拦截，必须是纯函数
├── persistence/
│   └── json-store.ts            # state.json 读写 + 迁移协调
├── app-config/                  # 真正的产品基础配置
│   └── index.ts                 # 用户/主题/字体/快捷键/端口/更新偏好
├── model-providers/             # LLM Provider 适配
├── assistants/                  # 助手 + Lorebook/Worldbook + 提示词注入
├── memory/                      # 记忆系统
├── search/                      # 搜索服务
├── tools/                       # 工具执行引擎 + 注册表
│   ├── mcp.ts
│   ├── local.ts
│   ├── skills.ts
│   └── execution.ts
├── inference-engine/            # 生成引擎（拆出前必须先重构 generateAnswer）
├── conversations/               # 会话 + 消息 + SQLite 活库
├── files/                       # 文件上传、OCR、文档解析
├── media/                       # TTS / ASR / 图像生成
├── backup/                      # 备份/恢复
│   ├── export.ts
│   ├── import.ts
│   └── storage.ts               # WebDAV/S3
├── api/                         # HTTP 路由 + SSE 基础设施
│   ├── router.ts                # 替代 routeApi() 的巨型 if/else
│   ├── sse.ts
│   ├── request.ts               # json/error/readJson/mime/staticCacheControl
│   ├── static.ts                # routeStatic
│   └── handlers/
└── app.ts                       # 组合根
```

### 4.2 依赖方向

```
foundation ──→ persistence ──→ domain modules ──→ api ──→ app
                     ↑
                app-config (被 foundation/net 通过参数使用)

domain modules 之间：
- model-providers, assistants, memory, search, tools 彼此不依赖
- inference-engine 依赖以上所有 domain
- conversations 被 inference-engine 和 api 依赖
- backup 读取所有 domain，但不被任何 domain 依赖
```

### 4.3 关键修正（与最初设想的区别）

1. **`persistence/sqlite` 合并进 `conversations`**：SQLite 只存会话，耦合极高。
2. **`event-bus` 属于 `api` 层**：SSE 广播被多模块调用，先作为 API 基础设施。
3. **`app-config` 不等于 `state.settings`**：`Settings` 是上帝聚合体，需要拆分。
4. **`inference-engine` 不能先拆**：`generateAnswer()` 是事务脚本，必须先剥离副作用。
5. **`tools` 与 `inference-engine` 有循环依赖**：必须先解除。
6. **`backup` 拆成 export/import/storage**：当前是上帝模块。
7. **`foundation/net.ts` 必须是纯函数**：当前直接读 `state.settings.proxyConfig`。

## 5. 迁移方案（分阶段，每阶段可独立回滚）

### 阶段 0：建护栏（必须先做，行为零改动）

**目标**：让编译器和测试为后续重构保驾。

1. 为 `pc-server` 添加 `tsconfig.json`。
2. 运行 `cd pc-server && bunx tsc --noEmit --skipLibCheck`，记录实际错误数（不一定是 72，取决于 tsconfig 严格度）。
3. 修复所有 tsc 错误（允许先禁用部分严格规则，但错误数必须清零）。
4. 在 `pc-server/package.json` 添加 `typecheck` 脚本。
5. 把 `bun run typecheck` 和 `bun run smoke:request-chain` 接入 CI/GitHub Actions。
6. 新增「备份往返」专项 smoke：
   - PC → zip → PC
   - PC → Android DB → PC
   - Android zip → PC
7. 不改动任何架构代码。

**验收标准**：
- `cd pc-server && bun run typecheck` 0 错误
- `cd pc-server && bun run smoke:request-chain` 通过
- 备份往返 smoke 通过
- CI 工作流更新成功

**关键注意**：`tsconfig.json` 需要配置 `types: ["bun"]` 或 `include @types/bun`，否则 `Bun` 全局类型会报错。

### 阶段 2：核心重构（必须先做，才能安全拆大热模块）

#### 任务 2.1：把 `generateAnswer()` 改成「只返回生成事件流」

这是整个重构**最关键**的一步，也是最难的一步。

**当前问题**：
`generateAnswer()` 内部直接调用：
- `saveState()`（写 state.json）
- `persistConversation()`（写 SQLite）
- `broadcastConversation()` / `broadcastNodeUpdate()`（推 SSE）
- 直接修改 `conversation.messages`

**目标**：
`generateAnswer()` 只负责：
1. 接收输入（assistant + messages + tools + memory + files）
2. 调用 Provider 流式生成
3. 处理工具调用循环
4. 输出生成事件流（text delta / reasoning / tool call / tool result / image / usage / error / complete）

调用方（`api` 层或 `inference-engine` 的 wrapper）负责：
1. 把事件流应用到 conversation
2. 调用 `persistConversation()` 写 SQLite
3. 调用 SSE 广播
4. 调用 `saveState()`

**实现思路**：
```typescript
interface GenerationEvent {
  type: 'delta' | 'reasoning' | 'tool_call' | 'tool_result' | 'image' | 'usage' | 'error' | 'complete';
  payload: ...;
}

async function* generateAnswer(params: GenerationRequest): AsyncGenerator<GenerationEvent> {
  // 只生成事件，不写状态
}
```

**验收标准**：
- typecheck 0 错误
- smoke 通过
- 流式对话功能与重构前完全一致
- 工具调用循环功能与重构前完全一致

#### 任务 2.2：解除 `tools` 与 `inference-engine` 的循环依赖

**当前问题**：`executeToolCall()` 执行完工具后直接调用 `generateAnswer()` 继续生成。

**目标**：`executeToolCall()` 只返回工具结果，由 `inference-engine` 决定是否继续生成。

**实现思路**：
- `generateAnswer()` 内部调用 `executeToolCall()` 拿到结果。
- `executeToolCall()` 不再调用 `generateAnswer()`。
- 如果工具执行后需要继续生成，`generateAnswer()` 的循环自己处理。
- `executeToolCall()` 内部也不再直接调用 `saveState()` 和 `broadcastConversation()`，这些副作用由调用方处理。

**验收标准**：

## 7. Git 版本管理纪律

**必须遵守**：

1. **一个模块一个 commit**：不要在一个 commit 里拆两个模块。
2. **纯搬迁和逻辑改动分开 commit**：拆分 commit 里只能有文件移动和 import 调整。
3. **每个 commit 必须通过**：
   - `cd pc-server && bun run typecheck`
   - `cd pc-server && bun run smoke:request-chain`
   - 备份相关改动额外跑备份往返 smoke
4. **commit message 用中文**，格式：
   ```
   refactor(pc-server): 提取 foundation/net 模块

   - 将代理系统从 server.ts 迁出
   - resolveEffectiveProxy 改为接收 ProxyConfig 参数
   - 行为不变
   ```
5. **绝不使用 Claude/AI 作为 commit author**（用户明确要求）。
6. **每步前先创建分支**：例如 `refactor/foundation-net`。
7. **发现 regression 立即 revert**，不要在同一分支上堆多个未验证的改动。
8. **阶段 2/3 的核心重构必须单独评审**：不能和阶段 1 的纯搬迁混在一起。
9. **阶段性 tag**：每完成一个大阶段（0/1/2/3/4），打一个 tag，例如 `refactor-phase1-complete`。
10. **不要提交 `pc-data/`**：该目录包含 API key，始终 gitignored。

### 2026-07-24 —— strictNullChecks 方案（动手前立案，5.4 类型硬化第二档）

**前因**：5.4 已开 noImplicitAny（第一档）。strictNullChecks 是第二档——未开时 null/undefined 可赋给任何类型，"undefined is not an object" 类运行时崩溃无法在编译期拦截。用户确认本轮推进（与 P1-2、P1-1 同批，依次做）。

**摸底**（2026-07-24）：开 --strictNullChecks 试编译，80 个错误 / 12 个文件。分析后归为三类：

1. **isRecord 收窄反噬（约 41 个，根因一个）**：`ToolErrorOutput`/`ToolPendingOutput` 的判别属性 `type?: undefined`——其声明类型本身是 undefined，不在 JsonValue 联合内。SNC 下这两个类型不再兼容 JsonValue → `ToolPart.output: ToolOutputEntry[]` 不兼容 → ToolPart 不兼容 `Record<string, JsonValue>` → 代码中大量 `isRecord(part) && part.type === "tool"` 的收窄把 ToolPart 从联合中剔除成 never（TS2367 无重叠比较 / TS2339 属性不存在于 never / TS2698 spread never）。
   - 已否决 `type?: never`：optional 属性对索引签名赋值的 undefined 豁免只豁免 optionality 附加的 undefined，不豁免声明类型本身解析出的 undefined（`?: never` 在非 exactOptionalPropertyTypes 下等价 `?: undefined`，最小复现已证伪）。
   - **定案：方案 B——JsonValue 对象臂放宽为 `{ [key: string]: JsonValue | undefined }`**。最小复现验证可行；真实代码库试编译错误 80 → 39，收窄反噬类全部消失。语义合理性：JSON.stringify 跳过 undefined 值属性，"值可能是 undefined 的对象"与 JSON 序列化语义一致；读取处的主流模式 `String(obj.x ?? "")` 天然兼容。
2. **真实的 possibly-undefined 解引用（约 16 个）**：update.ts 的 release.assets（GitHub API 可选字段）、providers.ts 的 hooks 可选回调（TS2722/TS18048）、state-load、storage、fonts。逐处局部收窄（?.、?? 兜底、提前 return），**行为不变**；确属逻辑缺陷的单独记录。
3. **smoke 脚本（22 个）**：request-chain-smoke.ts 把 `AnyRecord | null` 直接传给要求 `AnyRecord` 的参数。测试脚本，失败即抛错是预期行为，用非空断言或显式守卫修。

**实施原则**：类型层修复优先，运行时行为零变更；修复与开开关（tsconfig strictNullChecks: true）同一提交（原子，避免中间态 CI 红灯）；全套验证（typecheck + 66 单测 + 双 smoke + 前端）后提交。
