## 阶段0 全景与架构地图

**总体印象**:模块化搬迁的骨架是成立的——`server.ts` 从历史上的 3700+ 行瘦身到 383 行,只做端口解析、Bun.serve、Origin 白名单、关停钩子;18 个领域目录职责划分清晰;`foundation` 零反向依赖;tsconfig `strict: true` 已全开。但搬迁留下了三类"未完成的收尾":死 import、import 副作用驱动的启动、一处运行时循环依赖。

### 0-1 【P2】server.ts 291 个具名 import 中 272 个未使用

- 位置:`pc-server/server.ts` 1-167 行 import 块。
- 现象:脚本逐符号比对,除 `error`、`RUNNING_IN_CONTAINER`、`startAnalytics`、`routeApi`、`routeStatic`、`handleAuthTokenRequest` 等约 19 个符号外,其余 272 个(含 `message-builder` 全家 29 个、`providers` 16 个、`tools` 15 个等)在文件体内零引用——是历史大文件搬迁后残留的 import 块尸体。tsconfig 未开 `noUnusedLocals`,typecheck 不报。
- 影响:①新人无法从 import 判断 server.ts 的真实依赖;②这些死 import 目前**实际承担着模块加载顺序的隐式约束**(见 0-3),贸然删除会改变初始化顺序——清理必须与 0-3 的显式 bootstrap 一起做,不能单独"顺手删"。
- 建议:引入显式 `bootstrap()`(见 0-3)后一次性清理死 import,并在 tsconfig 开 `noUnusedLocals` 防复发。

### 0-2 【P2】运行时循环依赖:backup/storage → backup/import → persistence/state-load → backup/storage

- 位置:`backup/storage.ts:12`(引 `streamResponseToTempAndRestore`)→ `backup/import.ts:22`(引 `normalizeState`)→ `persistence/state-load.ts:25`(引 `normalizeS3Config/normalizeWebDavConfig`)。
- 现象:三条边都是运行时 import,且 `state-load.ts:482` 在模块顶层执行 `setState(loadState())`,`loadState → normalizeState → normalizeS3Config` 会在 `backup/storage.ts` 尚未完成求值时调用它的导出。今天不炸,仅仅因为环上所有符号都是提升的 `function` 声明(ESM 实例化阶段已可用)。
- 影响:任何人把 `normalizeS3Config` 改成 `const` 箭头函数、或在 storage.ts 顶层加一个被它引用的常量,启动就会 TDZ ReferenceError,且报错点在离改动很远的 state-load,极难排查。这是踩在语言实现细节上的平衡。
- 建议:`normalizeS3Config/normalizeWebDavConfig` 是纯配置规范化,不属于 backup 域,下沉到 `app-config/`(或 foundation)即可断环;`storage.ts` 对 `import.ts` 的依赖方向也值得反转(storage 是"云端字节搬运",不该知道"如何恢复")。

### 0-3 【P2】启动初始化散落在三处 import 副作用,顺序隐式依赖 import 顺序

- 位置:`persistence/state-load.ts:482-489`(setState(loadState()) + launchCount + 代理拦截器安装);`conversations/index.ts:188-194`(configureWorkingSet + startWorkingSetSweep);`api/sse.ts:64-68`(initWorkingSetSseGuard + initAppErrorBroadcast)。
- 现象:整个应用的启动序列 = "server.ts import 块的求值顺序 + 三处模块顶层副作用",没有一个显式的 `bootstrap()`。state-load 的注释还残留着对旧 server.ts 行号的引用("必须放在 activeSaveStatePromise 声明之后调用,否则撞 TDZ")——这句话描述的约束在新结构里已经由 import 顺序隐式保证,但没有任何机制守护它。
- 影响:①迁移(SQLite 灌库、记忆拆分、附件去重)在 *import 时刻* 运行,任何脚本/测试只要 import 了触达 state-load 的模块就会执行真实磁盘迁移——测试必须小心设置数据目录,新人极易踩坑;②未来做多标签页/Agent 化需要调整启动序列时,没有一个可以下手的编排点。
- 建议:把三处副作用收敛为 `bootstrap()` 显式函数,由 server.ts 在 Bun.serve 之前按序调用。这也是 0-1 死 import 清理的前置条件。

### 0-4 【P3】领域模块普遍反向依赖 api/(sse 广播 + logs)

- 位置:`conversations/orchestrator.ts`、`backup/import.ts`、`app-config/index.ts`、`tools/execution.ts`、`media/*`、`search/`、`model-providers/checks.ts`、`inference-engine/*` 等 15+ 文件 `import { broadcast* , touchStream } from "../api/sse"`、`import { addLog } from "../api/logs"`。
- 现象:`api/sse.ts` 和 `api/logs.ts` 实质是全局基础设施(事件广播总线 + 请求日志),却住在传输层目录下,导致目录级依赖矩阵里"人人依赖 api"。
- 影响:纯观感/分层问题,无运行时风险。但未来多标签页(每页独立 SSE 订阅)和 Agent 化(后台任务也要广播进度)都会加重对这两个文件的依赖,现在的位置会让"api 层"越来越名不副实。
- 建议:择机把 sse 广播骨架挪到 `observability/` 或独立 `events/` 模块,api/ 只保留 HTTP 端点接线。不阻塞发布。

### 0-5 【P3】foundation/types 子文件从自己的桶文件回环 import

- 位置:`foundation/types/settings/*.ts`、`dto.ts`、`parts.ts` 均 `import type {...} from "../index"`(即从聚合桶回引)。
- 现象:形成 12 文件的类型环。全部是 `import type`,编译期擦除,运行时无害。
- 建议:子文件之间直接互引(`./parts`、`./settings/model-layer`),桶文件只负责聚合导出。低优先级。

### 0-6 【记录】阶段0确认无恙的项

- `foundation/` 对上层零运行时依赖(rg 全量验证)。
- 无任何模块反向 import `server.ts`(旧架构最大的耦合源已消除)。
- 端口解析优先级(--port > PORT > 用户设置 > 8080)、容器不跳端口、`port_in_use:` 标记、`RIKKAHUB_PORT:` 标记与 Tauri 壳的契约完整。
- Origin 白名单逻辑(无 Origin 放行/null 拒绝/tauri 协议放行/Host 一致放行)读了一遍,语义正确;`/api` 之外的静态资源不拦,合理。
- Linux 启动时对 unzip/zip/wl-copy/espeak-ng 的缺失探测并告警,对 Linux 二进制用户友好。
- 关停钩子 SIGINT/SIGTERM → flushConvDirtyNow + WAL checkpoint,方向正确(具体时序留阶段2细查)。
- 已知项不重复记录:`maxRequestBodySize` 64GB 过大(收官审查已立案"近P0批")。

## 阶段1 foundation + persistence + app-config

**总体印象**:这是全项目质量最高的一层。temp+rename 原子写纪律、三条迁移链(SQLite 灌库/记忆拆分/附件去重)的幂等设计与防御层、代理拦截器的 per-request 现读,都达到了商业应用水准。问题集中在"承诺了但没人兑现"的收尾:两个为安全性而写的函数(flushSaveState / saveInitialState)是死代码,recovery 文件写了永远没人读——防线画在图纸上,没接进电路。

### 1-1 【P1】关停不刷 state.json:flushSaveState 是死代码,shutdown() 直接 process.exit

- 位置:server.ts:359-370(shutdown);persistence/json-store.ts:128(flushSaveState 全项目零调用)。
- 现象:shutdown 只做 flushConvDirtyNow + WAL checkpoint 就 exit(0)。飞行中的 state.json 异步写(Bun.write + rename,Windows 杀毒锁时退避重试可拉长到秒级)、节流定时器里挂着的待写、coalesced 尾随写全部被杀。flushSaveState 注释自称"Used by graceful shutdown paths",实际没有任何 shutdown 路径调用它;且它本身只 await 当前 promise 引用,不追 finally 里新起的尾随写(拿到旧引用即返回),即使接上也兜不住最后一笔。
- 场景/影响:改设置后 1 秒内退出 → 设置/files 账本/统计丢最后一笔。另注意 Windows 上 Tauri 关窗是 TerminateProcess,信号钩子根本不运行——原子写保证不撕裂,但"最后一笔必达"在三形态上都不成立。
- 建议:shutdown 改 async:清节流定时器→立即 saveState→循环 await activeSaveStatePromise 直到为 null→再 exit;flushSaveState 修为循环追引用。Windows 关窗路径依赖 200ms 节流上限自愈,可接受但要写进文档。

### 1-2 【P1】recovery 文件写了永远不读,损坏回退却认几个月前的化石快照

- 位置:json-store.ts:85-91(写 recovery + 报"重启后自动恢复");state-load.ts:259-277(损坏回退只认 state.json.pre-sqlite.bak)。
- 现象:performStateSave 八连败后先做一次**非原子直写** state.json(此刻被杀即撕裂),再败才写 state.json.recovery-<ts>.json,错误文案承诺"重启后自动恢复"。而 loadState 解析失败的回退顺序是:pre-sqlite.bak(1.2.6 迁移时代的快照,对老用户可能落后数月)→ 默认状态。recovery-*.json 全项目零读取。
- 场景/影响:磁盘满/锁风暴下触发兜底直写→中途被杀→state.json 撕裂→下次启动静默回滚到远古设置(API key、供应商、助手全回到几个月前),而磁盘上明明躺着最新的 recovery 文件。
- 建议:损坏回退顺序改为:最新 recovery-*.json → 滚动近期备份(见 1-3)→ pre-sqlite.bak → 默认;删掉非原子直写那一步(直接走 recovery 路线);恢复成功后把用到的 recovery 归档。

### 1-3 【P2】state.json 无滚动近期备份

- 位置:persistence 全域。
- 现象:仅有的两份备份(pre-sqlite.bak / pre-memory-split.bak)都是一次性迁移时代的化石,之后 state.json 再无任何时间点副本。会话有活库+WAL+导入前快照,设置层(供应商 apiKey、助手、记忆配置)反而是裸奔的单文件。
- 建议:每日首个 saveState 成功后 copy 一份 state.json.daily.bak(仅一代即可),配合 1-2 组成完整恢复链。

### 1-4 【P2】.tmp 残留无人清扫(用户真实数据目录实测 6 个)

- 位置:json-store.ts:68/137/158(三种 tmp 命名);loadState 无清扫逻辑。
- 现象:重试循环中 rename 失败且 unlink 也失败(Windows 反病毒锁窗口两连击)会留下全量 state 副本;审查当日在真实用户数据目录(D:/SoftWare/Rikkahub/pc-data)实测躺着 6 个 state.json.*.tmp,时间跨两个月,证明该路径在生产环境真实发生。每个 tmp 都是含全部 apiKey 的完整 state 副本,永久堆积。
- 建议:启动时(loadState 尾部)清扫 state.json.*.tmp / *.migrate.*.tmp / *.mem-migrate.*.tmp。

### 1-5 【P2】双实例同 dataDir 无互斥锁

- 位置:foundation/paths.ts(dataDir 无 lockfile);server.ts 端口顺延逻辑。
- 现象:Tauri 有 single-instance 插件,但 Linux 裸二进制/Docker 误双开时,第二实例端口自动顺延成功启动,两进程共写同一 dataDir:state.json last-writer-wins 互相覆盖(A 实例改的设置被 B 实例的旧内存整包冲掉),SQLite 靠 WAL 扛住但脏节流交错。
- 建议:dataDir 写 pid lockfile(启动检查存活,陈旧则接管),冲突时拒绝启动并给出明确提示。

### 1-6 【P2】StoredFile.path 存绝对路径,数据目录搬家即全部附件 404

- 位置:foundation/types/index.ts:259(path 契约);api/handlers/files.ts:48(existsSync(entry.path) 失败直接 404,无 filesDir 回退)。
- 现象:上传时写入绝对路径(join(filesDir,...)),读取只认这条绝对路径。本应用是便携式布局(pc-data 随 exe),用户移动安装目录/换盘符/迁移新机(拷目录不走备份)后,所有附件/生图/头像 404——字节都还在 files/ 里,账本却指向旧盘符。
- 建议:读取统一回退 join(filesDir, basename(path));或迁移为相对路径+启动一次性修正。全链路(含 media/生图写入方)留待阶段5 细查。

### 1-7 【P2】附件抽取全文(extractedText)驻留 state.json

- 位置:foundation/types/index.ts:263;files 上传时写入。
- 现象:每个文档附件的抽取全文永久存进账本。几十个大 PDF 即可把 state.json 推到几十 MB,而 message-builder 仍有 200ms 节流全量重写(json-store 注释里那场"100MB state.json 事故"的结构性残余)。会话已拆 SQLite,这是下一个同类地雷。
- 建议:extractedText 拆到 files/<id>.extracted.txt 惰性读取,账本只留长度/摘要。

### 1-8 【P2】saveInitialState 死代码:启动规范化结果不落盘

- 位置:json-store.ts:169(全项目零调用);state-load.ts:483(launchCount 内存自增)。
- 现象:normalizeState 的全部 backfill/迁移标记(如 provider-reorder)只活在内存,要等下一次任意 saveState 才落盘。纯只读会话(启动→看历史→退出)每次启动重跑全部规范化;launchCount 在这类会话中永不落盘,统计失真。
- 建议:并入 0-3 的显式 bootstrap():启动完成后调一次 saveState。

### 1-9 【P3】backupStamp 用 UTC,与安卓本地时间戳错位

- 位置:foundation/utils.ts:114-117。注释声称对齐安卓 DateTimeFormatter(本地时区),实际 toISOString() 是 UTC——中国用户导出的备份文件名时间早 8 小时,跨端文件名排序错位。一行修复,建议顺手改。

### 1-11 【记录】阶段1确认无恙的项

## 阶段2 conversations + assistants 域

**总体印象**:DB-first 架构(活库权威 + working set 单实例注册表 + 脏标记节流 flush)设计与实现质量高,防御性注释密度全项目最高。但复查时发现一个踩在 SQLite 语义陷阱上的 P0(2-0):它让"流式增量落库"在进程死亡场景下变成数据粉碎机——这是全项目目前最严重的隐患。

### 2-0 【P0】INSERT OR REPLACE 会话行 + foreign_keys=ON = 级联清空该会话全部消息节点(复查新增)

- 位置:conversations/index.ts:231-246(upsertConversationRow 用 INSERT OR REPLACE)+ 332-364(flushConvDirty 先 upsert 会话行、再只补写脏节点)+ 65-88(PRAGMA foreign_keys=ON;pc_message_node 对 pc_conversation ON DELETE CASCADE)。
- 现象:SQLite 的 REPLACE 冲突解决 = 隐式 DELETE+INSERT;外键开启时该隐式 DELETE **触发 ON DELETE CASCADE**。已用 :memory: 库实证:对已存在的会话行执行 INSERT OR REPLACE,其 3 条子节点行变 0。
- 触发链:流式每个 chunk → touchStream 标脏会话行+节点 → 200ms flushConvDirty → 先 upsertConversationRow(**级联清空该会话全部节点行**)→ 再只补写脏节点。即:**整个流式期间,磁盘上该会话只剩正在生长的那(几)个节点**;全部历史仅存于内存,直到流结束 completeConversationGeneration 的全量 persistConversation 才写回。
- 场景/影响:流式中途进程死亡 = 该会话历史永久丢失(重启后只剩最后一个节点)。触发面极宽:①崩溃/断电;②Windows 关窗 = TerminateProcess,钩子不运行(1-1);③**优雅关停也丢**——shutdown() 只 flushConvDirtyNow(又一次 wipe+部分补写),不对生成中会话全量 persist,流式中 Ctrl+C / docker stop 同样丢;④应用内更新重启。次生:级联删不触 FTS 虚表(无外键),事后搜索残留幽灵命中。
- 为何至今无人定位:working set 让 UI 全程读内存,流一结束就全量写回——只有"流式中途死进程"暴露,恰是用户最说不清、开发最难复现的场景。历史上零星"会话只剩最后一条"类反馈很可能就是它。
- 建议(紧急,建议不等审查收官单独成批修):upsertConversationRow 改用 upsert 子句(INSERT ... ON CONFLICT(id) DO UPDATE SET ...,不删行、不触发级联);migrateConversationsIntoDb/persistConversation 的 REPLACE 可保留(总是随后全量重插节点)。同批把 shutdown() 补上"对 generating 会话 abort → 全量 persistConversation"。回归验证:流式中 kill -9,重启断言节点数完整。

### 2-1 【P1】regenerate / 消息编辑 / compress 入口不中止进行中的旧流(send/stop 有守卫)

- 位置:api/handlers/conversations.ts:241-279(regenerate)、313-348(messages/edit)、402-415(compress);对照 send 入口 140-142 的 abort + finishInterruptedPendingTools 序列。

## 阶段4 api 层 + server.ts + 通信协议

**总体印象**:安全基线做得比预期扎实——Origin 白名单 + 可选密码鉴权(HMAC 无状态 token、timingSafeEqual、5 次/60s 节流、恒定延迟)、默认只绑 127.0.0.1 且暴露即告警、全部文件服务端点都有 traversal 防护、导入走磁盘流式不吃内存、端口顺延对容器收敛。问题集中在一处:SSE 广播对"已断开的客户端"零防御,而其中一条路径在定时器里抛未捕获异常——已实证会直接杀掉整个进程。叠加全项目没有任何 uncaughtException 兜底,这是本阶段的头号隐患,且路线图的多标签页/局域网多端会把它从"极窄竞态"放大成"高频崩溃"。

### 4-1 【P1】SSE 广播裸 enqueue 死连接抛错;节点广播在定时器里抛 = 整进程崩溃

- 位置:api/sse.ts:141-143(broadcastConversation)、159-161(broadcastNodeUpdateNow)、114(broadcastSettings)、131(broadcastList)、69(errorClients)全部 `client.enqueue(...)` 无 try/catch;唯独 broadcastMemoryUpdate(124-126)包了。崩溃路径:scheduleNodeBroadcast:49 `setTimeout(flushNodeBroadcast)` → broadcastNodeUpdateNow → 裸 enqueue。
- 实证:①对已 cancel 的 ReadableStream controller 调 enqueue 抛 `TypeError: Invalid state: Controller is already closed`;②`setTimeout` 回调里抛未捕获异常,Bun 进程直接退出(exit=1,后续定时器不再执行)。二者叠加 = 崩溃链成立。
- 触发链:某会话 SSE 客户端断开(关标签页/网络掉线/Docker 反代超时),其 controller 已关闭但 openSse 的 cancel() 尚未把它从 conversationClients 摘除的窗口内,流式正在跑的 200ms/33ms 节点广播经 setTimeout 触发 → enqueue 抛错 → **定时器内未捕获 → 整个 Bun 服务进程退出**,该机器上所有用户的全部会话流式、SSE、请求全断。
- 场景/影响:单用户本机窗口窄(优雅关标签页时 cancel 通常先跑),但网络掉线的检测有延迟——局域网/Docker 多端部署下这个窗口显著变宽,且是路线图明确方向。次级(同步路径):从 handler 直接调的 broadcastConversation/List/Settings 若在遍历中途 enqueue 抛错,会中断整个 for 循环 → 后面的存活客户端收不到本次事件(静默丢事件),并把 500 冒泡回请求。
- 建议:所有广播的 enqueue 统一包 try/catch(对齐 broadcastMemoryUpdate),catch 里把该 controller 从对应集合移除(不只是吞掉,否则死 controller 永久驻留反复抛);heartbeat 已有的"抛错即清理"模式可复用。与 4-2 同批。

### 4-2 【P1】全项目无 uncaughtException / unhandledRejection 兜底,任何异步抛错都能掀翻整服务

- 位置:server.ts 仅注册 SIGINT/SIGTERM(372-373),无 process.on("uncaughtException")/("unhandledRejection")。
- 现象:fetch 主处理器有 try/catch(288-291)兜住请求内同步/await 抛错→500,但**定时器回调、游离 Promise、SSE stream 内的 setTimeout**都在这张网之外。4-1 是具体实例,但面更宽:json-store 尾随合并写的游离 promise(阶段1 1-10 已记)、scheduleNodeBroadcast/scheduleThrottledConvFlush 的定时器、各 fire-and-forget(startAnalytics/loadModelsDev/runPostGenerationTasks)一旦抛到顶层都是全进程退出。
- 影响:成熟商业应用(尤其要服务多用户的 Docker/局域网形态)一次未预期异步抛错 = 全体掉线,而非降级单个请求。
- 建议:进程级注册 uncaughtException/unhandledRejection → reportError 上报 + 记日志 + 不退出(除非是启动期致命错误);与 4-1 的逐点 try/catch 形成纵深(逐点防已知热路径,全局网兜未知)。

## 阶段5:backup 域 + files 域(刚重构,重点)

### 5-1【P0】PC zip 恢复重置 nextFileId=1,按新 id 覆写磁盘上现有附件字节——两条现实路径造成不可逆数据损毁

链条(全部为代码直读证实,无推测):

1. `import.ts:142`:PC 恢复(zip 内有 `pc-backup.json`)一进来就 `{ ...incoming, files: [], nextFileId: 1 }` → `normalizeState`(`state-load.ts:215-219` 取 `max(nextFileId, 文件id+1, 1)`,files 为空即保持 1)。
2. `import.ts:204-220` `registerStaged`:`newId = state.nextFileId++`(从 1 起),`writeFileSync(join(filesDir, newId+ext), ...)`——而本机现有附件的落盘命名正是 `filesDir/<id>.<ext>`(`api/handlers/files.ts:20` 上传时如此分配)。**同 id 同扩展名时,现有附件字节被备份内容直接覆写,无任何快照**(会话库有 `snapshotConversationsDbBeforeImport`,文件没有对应物)。

恶果一(降级路径,静默错乱):`import.ts:161-190` 的"收官 P0-1"守卫在 zip 缺会话库/ dump 损坏时降级为 settings-only,报错文案承诺"现有会话保持不变"。但 **files 替换与字节覆写无条件执行**——保留下来的现有会话,其消息里 `/api/files/<旧id>/content` 现在指向 zip 里完全不同的文件(或悬空),旧字节已被覆写销毁。触发面并不小:所有"备份 2.0 之前"的纯 PC 用户 zip(无 `pc_conversations.db` 也无 `rikka_hub.db`)导入时全部落进该路径。

恶果二(中途失败,半途状态+字节已毁):re-link 的写盘发生在 `finalize`/`saveState` 之前,途中任何异常(磁盘满、单个 writeFileSync 失败)由外层 catch 原样上抛 → 磁盘 state.json 仍是旧状态,但旧附件字节已被覆写;更糟的是 `setState` 已把**内存** state 换成了半导入状态,此后用户任意操作触发 `saveState` 就会把半导入状态持久化。老 JSON 备份路径(`applyBackupPayload:83-94`,按原 id 写 `filesDir/<id>.<ext>`)同属此列。

恶果三(缓存假设被打破):`api/handlers/files.ts:57-63` 对 `/api/files/<id>/content` 发 `Cache-Control: immutable` + `ETag:"<id>"`,注释明言"id 对应内容永不变"。恢复覆写后同 id 换内容,浏览器端将长期显示旧图。

修复方向(实施时再定):恢复时**不重置 nextFileId**(沿现有 id 空间单调续分配,天然零覆写,旧孤儿字节留待清理);或 re-link 先写临时目录、全部成功后原子换名;配套在导入前对 state.json+filesDir 做轻量快照,与会话库快照对齐(见 5-6)。

### 5-2【P1】导出打包 spawnSync 硬超时 120s,多 GB 附件库导出必然撞墙

`export.ts:552/560`:Windows(PowerShell `CreateFromDirectory`)与 Linux(`zip -rq`)都带 `timeout: 120_000`。代码注释自述支持"multi-GB attachments、zip 可超 4GB"(`export.ts:365-368`),但机械盘/低速盘上压缩数 GB 极易超过 120s → 进程被杀 → 导出报"Zip creation failed"。导入侧解压(`import.ts:296/301`)反而无超时,不对称。云备份(WebDAV/S3)与本地导出共用此函数,同样受限。

### 5-3【P1】附件 staging 失败被静默吞,产出"看似成功"的不完整备份

`export.ts:517-521`:逐文件 `writeFileSync(readFileSync)` 的 catch 只 `console.warn`,不计数、不 reportError、不影响导出结果。磁盘满(corner 清单"备份中途磁盘满")、文件名含 Windows 非法字符(见 5-4)时,备份 zip 缺附件但用户拿到的是成功响应与正常大小的 zip。对照:源文件缺失(missingSkipped)有 reportError 警告,staging 写失败反而没有——恰好是更严重的那种。

### 5-4【P2】上传 fileName 未消毒:导出 staging 存在自伤性路径穿越与必败字符

`api/handlers/files.ts:22` 原样保存客户端 `file.name`;导出 `export.ts:441-450` 直接 `name = file.fileName` 后 `join(uploadStage, name)`(518):

### 5-5【P2】备份/恢复重 IO 全同步 + spawnSync,分钟级冻结整个事件循环

导出:staging 全量 `readFileSync/writeFileSync` 复制 + 尺寸碰撞组 sha256 + spawnSync 压缩;导入:spawnSync 解压 + 全量逐文件复制 + sha256 去重。多 GB 场景下单线程 Bun 事件循环整体冻结数十秒到数分钟:SSE 心跳停摆、所有 API 无响应、onProgress 在压缩/解压阶段根本无法送达(spawnSync 期间连消息都发不出)。对未来 workspace/多 tab 常驻形态伤害更大。方向:Bun.spawn 异步化 + 复制/哈希分批让出事件循环。

### 5-6【P2】恢复无 state.json 预快照,选错备份即不可逆

### 8-2【P2】Tauri 形态退出永远是硬 kill,服务端优雅停机路径在最主流的部署形态下从不执行

- 【现象】Windows 上 `child.kill()`=TerminateProcess,Bun 进程的 SIGTERM 处理器不会运行。`shutdown()` 里的活库脏行冲刷与 WAL TRUNCATE checkpoint 只在裸二进制 Ctrl+C 和 Docker stop 时执行;Windows/Tauri(用户基数最大)每次退出都是强杀。
- 【场景】依赖 WAL+200ms 节流冲刷,常态下丢失窗口很小(最后 ≤200ms 的脏行),不损坏。但生成中退出(与发现 2-0 的 abort→persist 叠加)、以及 WAL 长期不 checkpoint 导致 -wal 文件膨胀,都在 Windows 形态下无解。
- 【建议】壳在 kill 前先发一个 HTTP 停机请求(如 POST /api/app/shutdown,server 执行 shutdown() 逻辑后自退),超时 2-3 秒再 kill 兜底。与 2-0 的修复合并设计。

### 8-3【P2】Linux 裸二进制放进无写权限目录时,启动即裸栈崩溃,无提示无回退

- 【位置】`pc-server/persistence/state-load.ts:251-252`(loadState 顶层 `mkdirSync(filesDir)`);`foundation/paths.ts:15`(dataDir=exe 同级 pc-data)
- 【现象】用户把 tar.gz 解压到 /opt 等 root 属主目录、以普通用户运行(README 场景之外但极常见),`mkdirSync` 抛 EACCES,模块顶层副作用直接把进程带崩,只有原始堆栈,没有"目录不可写,请用 RIKKAHUB_PC_DATA_DIR 指定数据目录"之类的提示,也不回退 XDG 数据目录。
- 【场景】Linux 新用户第一次跑就崩,错误信息不可理解。update/apply 对应用目录不可写的场景倒是有友好报错(对比不对称)。
- 【建议】启动时捕获 dataDir 创建失败,输出明确指引(或回退 ~/.local/share/rikkahub 并提示)。

### 8-4【P2】初始化依赖模块导入副作用:server.ts 导入 loadState 却从不调用,saveInitialState 无人调用

- 【位置】`pc-server/persistence/state-load.ts:482-489`(模块顶层 `setState(loadState())`+代理拦截器安装);`server.ts:17`(import 后零调用);`json-store.ts:169`(`saveInitialState` 导出后全仓零调用);state-load.ts:473-505 残留三段无主注释
- 【现象】整个应用的状态装载、迁移链、代理拦截器安装都发生在"import 这个模块"的副作用里。server.ts 的 `import { loadState }` 看似未使用实则承重——若被人当死代码清掉(或未来换打包器做 tree-shaking),服务启动即 `state` 未初始化崩溃。`saveInitialState` 及其"必须在 TDZ 之后调用"的注释是搬迁遗留的死代码,与实际执行路径矛盾。
- 【场景】纯维护性地雷,当前行为正确。但这与 paths.ts 头注释里记录过的"搬文件漏改 import.meta.dir 导致 rootDir 失联"是同一类事故的温床。
- 【建议】改为 server.ts 显式 `setState(loadState())`,删除 state-load.ts 顶层副作用与死代码/无主注释。

### 8-5【P3】Docker 与 Linux 裸包缺 icons/(Docker 还缺 fonts/),品牌图标全部降级灰字母

- 【位置】`.dockerignore:13`(显式排除 icons/);`Dockerfile:67-69`(只拷二进制+web-ui);`build-linux.yml:80-82`(拷 fonts 不拷 icons);`assets/icons.ts:81-97`(优雅降级首字母 SVG)
- 【现象】Tauri 形态通过 bundle resources 带全 icons/fonts;Docker/Linux 裸包两形态所有供应商/模型图标显示为灰底首字母,Docker 内置字体列表为空(自定义字体在 pc-data/fonts 不受影响)。
- 【建议】Dockerfile 增加 `COPY icons/ fonts/`(并从 .dockerignore 放行 icons),build-linux.yml 补 `cp -r icons`。均为一行修复。

### 8-6【P3】Docker 以 root 运行、无 HEALTHCHECK

- 【位置】`Dockerfile`(distroless/base 默认 root,未用 :nonroot 变体,无 USER 指令,无 HEALTHCHECK)
- 【现象】bind-mount 的 pc-data 里所有文件 root 属主,宿主普通用户读写要 sudo;编排系统无健康探针可用。
- 【建议】评估切换 `distroless/base-debian12:nonroot` + 文档说明卷属主;HEALTHCHECK 可用 `["/app/rikkahub-pc","--healthcheck"]` 之类自查子命令实现(distroless 无 shell/curl)。

### 8-7【P3】NSIS 以固定文本模式解析 user-config.json,非 ASCII 数据目录路径存在解析/回写风险

- 【位置】`installer-hooks.nsh:81-121`(按字面 `"data_dir": "` 前缀+固定缩进逐行找)、130-141(FileWrite 回写)
- 【现象】解析依赖两个写入方(serde_json pretty / NSIS 自身)的确切格式,任何格式漂移都会静默回退"全新安装"默认路径——即注释里自己警告的"孤儿化旧数据"场景。且 NSIS FileRead 按 ANSI 代码页解码 UTF-8 文件,中文路径会得到乱码,POSTINSTALL 再把乱码写回。安装页文案也自知("路径里最好不要包含中文字符")。
- 【建议】用 nsJSON 插件或让 Rust 壳提供只读命令行查询;至少在读回值后校验目录存在性,不存在则不跳过选择页。

### 8-8【P3】降级到 <1.2.6 版本后再升级,降级期间新建的会话被静默丢弃

- 【位置】`state-load.ts:507-556`(迁移标记早退)、`json-store.ts:60-65`(瘦身写盘)
- 【现象】瘦身后的 state.json 无 conversations,老版本(<1.2.6)视为空库但不损坏现库(rikka_hub.db 原样保留)。用户在老版本里新聊的会话写进 state.json.conversations;再升回来时迁移标记已存在→`migrateConversationsIfNeeded` 早退,这批会话不进活库,下次 saveState 把它们从 state.json 抹掉。降级到 ≥1.2.6 无此问题。
- 【建议】低优先:标记已存在但 parsed.conversations 非空时,做一次增量合并(仅插入活库不存在的 id)再瘦身。

### 8-9【P3】state.json 损坏走 pre-sqlite.bak 兜底时,settings 静默回滚到远古时点

- 【位置】`state-load.ts:259-277`
- 【现象】损坏兜底读的是 1.2.6 迁移时刻的完整备份:settings(供应商/API Key/助手)整体回到当年,且该 bak 无迁移标记,其远古 conversations 会被重新灌进当前活库与现有数据合并(INSERT OR REPLACE 语义下同 id 老会话覆盖新会话,与发现 2-0 关联)。
- 【建议】兜底时打 error 级 app-error 告知用户"配置已从 X 年备份恢复";重灌前检查活库非空则仅补插缺失 id。

### 8-10【P3】Linux 原地更新先换 web-ui 再换二进制,失败时前后端版本错位;fonts 不随更新替换

- 【位置】`api/handlers/update.ts:288-349`
- 【现象】web-ui 替换成功后若二进制 swap 失败(返回 500),磁盘上是新前端+旧后端,routeStatic 每请求重读即时生效,前端可能调用旧后端不存在的 API。另 tar.gz 里的 fonts/ 目录不在 apply 替换范围,内置字体新增无法通过原地更新到达用户。
- 【建议】二进制先行或失败时回滚 .web-ui.bak;apply 顺带同步 fonts/。

### 8-11【P3】shutdown() 未 await flushSaveState;launchCount 等启动期变更不落盘

- 【位置】`server.ts:359-370`;`json-store.ts:128-132`(flushSaveState 全仓零调用);`state-load.ts:483`(launchCount+1 仅内存)
- 【现象】停机时在途的异步 state 写不等待(原子性保证不损坏,最多丢最后一笔);启动期 normalizeState 的迁移标记(如 provider-reorder)与 launchCount 自增只活在内存,首次用户操作触发 saveState 前退出则下次重跑(均幂等,无实害)。
- 【建议】shutdown 里 `await flushSaveState()`(需把 shutdown 改 async+process.exit 放最后);顺手删掉或用上 saveInitialState。

### 8-12【P3】Rust/Tauri 侧零 CI;docker-publish 对所有分支推送都发布镜像

- 【位置】`.github/workflows/ci.yml`(仅 bun typecheck/test/smoke);`docker-publish.yml:4-5`(branches: ['*'] 即推即发 ghcr)
- 【现象】lib.rs 606 行 Rust 代码无 cargo check/clippy 门禁,坏改动要到本地 tauri build 才暴露;任意实验分支 push 都会向 ghcr 发布可拉取镜像(tag=分支名),用户误拉风险小但存在。
- 【建议】ci.yml 加 cargo check(可仅在 src-tauri 变更时触发);docker-publish 收敛到 main+tags。
