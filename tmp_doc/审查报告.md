# Rikkahub Desktop 架构审查报告

> 审查日期：2026-07-19　|　审查对象：v1.4.1（git e322d8c）
> 审查方式：主线人工审查（后端核心）+ 三路专项子审查（前端 / 备份与跨端兼容 / Provider 流式管线）
> 文档性质：面向开发者的架构审查。后续的修复/重做方案将在本文档基础上续写。

---

## 0. 结论先行

**根源性问题只有一个：这个项目没有架构，只有实现。**

"架构"意味着三样东西：模块边界、依赖方向、接口契约。三者在本项目中均不存在：

- **没有模块边界**——持久化、Provider 客户端、工具调度、备份、TTS/ASR、搜索、代理、路由等十几个本应独立的子系统全部共享 `pc-server/server.ts`（18,246 行 / 811 KB / 614 个顶层声明）的同一个模块作用域，任何函数可以直接调用任何函数、直接读写全局可变单例 `state`（`state.settings` 被引用 268 处）。不存在任何一个可以单独理解、单独修改、单独测试的单元。
- **没有依赖方向**——106 个路由分支每个都把"业务逻辑 + 持久化 + SSE 推送"三层内联在同一个 `if (path === ...)` 块里，不存在路由层→服务层→存储层的单向依赖。
- **没有接口契约**——前后端类型靠人工抄写同步；后端从未配置过类型检查（无 tsconfig、无 typecheck 脚本），手动运行 `tsc --noEmit` 得到 **72 个类型错误**；子系统之间的"契约"就是直接读写对方的内存；唯一的测试手段是 2,152 行的端到端 smoke 脚本，因为没有任何接口缝可以做单元测试。

由此产生的直接后果：无法分离式开发（人与人、人与 AI 均无法并行安全修改）、备份等子系统无法独立演进、每次更新与拓展都是全局回归风险。

**决策建议：修复（渐进式模块化），不要重做。** 详细论证见 §6。核心理由：项目的核心资产不是代码结构，而是沉淀在代码里的数百个实战边界修复（Bun 代理 env 快照锁、Android 枚举兼容、FTS5 影子表、Windows 文件锁重试、SSE 连接风暴治理等）；重写等于让大量老用户把这些雷重新踩一遍。而 `bun build --compile` 对多文件项目同样输出单 exe——"单文件源码方便编译发布"这一原始理由在技术上不成立，拆分是零发布代价的。

## 2. server.ts 内部实况（模块地图）

单文件内混居的子系统（按文件内行序）：

1. **类型定义**（~37-500）：Model / Provider / Assistant / Settings / Conversation / State 等，但大量字段类型为 `JsonValue`，实际 shape 只存在于使用处的运行时假设中。
2. **默认配置与提示词模板**（~500-1560）：defaultProviders / defaultAssistant / defaultSettings / 六七个默认提示词常量。
3. **记忆存储层**（1571-2260）：`memoryStore` 对象字面量，管理 `pc-data/memory/` 三个 JSON 文件，自带串行写队列与原子写。（已做**数据层**分离，但代码仍在单文件内。）
4. **状态持久化**（2138-2790）：loadState / normalizeState / performStateSave（原子写 + 8 次重试 + 兜底 recovery 文件）/ saveState（节流合并）。
5. **代理系统**（2355-2690）：Windows 注册表 / GNOME gsettings 读取、`globalThis.fetch` 全局拦截器、bypass 规则（含 CIDR 匹配）、错误分类。
6. **SSE 基础设施**（2844-2960）：openSse / 四路广播（settings、memory、list、conversation）/ 30fps 节流合并。
7. **消息与变换管线**（3084-3470）：message 工厂、think-tag 变换、正则变换、模板变量、注入。
8. **备份与跨端互转**（3830-6180）：PC zip 备份、Android zip 导入（含 avatar 重写、file URL 重写）、为 Android 生成 Room 兼容 SQLite（generateRikkaHubDb）、WebDAV 客户端（自制 XML 解析）、S3 客户端（自制 AWS SigV4 签名）、**自制 ZIP 读写**。
9. **会话 SQLite 活库**（4802-5300）：WAL、脏标记、200ms 节流 flush、损坏隔离重建、1.2.6 迁移。
10. **注入系统**（6182-6400）：模式注入 / Lorebook / 系统提示词注入 / 安全插入点查找。
11. **搜索服务**（6396-7500）：17 个搜索引擎实现 + 密钥轮换 failover + 自定义 JS 搜索沙箱。
12. **工具系统**（7449-8450）：openAiSearchTools / openAiSkillTools / openAiLocalTools / openAiMcpTools 声明、MCP 客户端（JSON-RPC、SSE endpoint 发现、session 缓存）、executeToolCall 调度器、审批状态机、PowerShell / 剪贴板 / 系统 TTS。
13. **文档解析**（8588-9370）：**自制 ZIP 解析、自制 XML pull 解析器、EPUB/DOCX/PPTX 文本提取**、mupdf PDF 提取。
14. **三家 Provider 消息编码**（9374-10660）：OpenAI Chat Completions / Responses API、Claude blocks、Google contents 三套互相独立的消息格式转换。
15. **Provider 测试与模型拉取**（10662-11330）：fetchProviderModels / fetchProviderBalance / runProviderCheck。
16. **图标与字体服务**（11325-11680）。
17. **流式管线**（11683-14300）：callProviderStreaming 及三家 provider 各自的流读取器与工具循环（详见子审查 §5.3）。
18. **图像生成 / TTS / ASR**（14286-15320）：含火山引擎二进制 WebSocket 帧协议。
19. **生成主链路**（15317-15475）：generateAnswer / 后处理任务。
20. **路由表**（15475-18035）：106 个分支的单函数 `routeApi`。
21. **静态服务与启动**（18035-18246）：routeStatic / 端口顺延 / Tauri 握手标记 / shutdown。

**要点**：上述每一项在现代工程里都应是独立模块（甚至独立包）。其中第 8、13 两项（自制 ZIP/XML/SigV4/文档解析）是典型的"应引依赖却手写"——手写本身质量尚可，但它们进一步膨胀了单文件，并让备份兼容逻辑与运行时纠缠。

## 3. 主线审查确认的问题清单（后端核心）

### P0（根源性 / 数据与安全风险）

- **P0-1 无架构**（见 §0）。所有后续 P1/P2 问题几乎都是它的症状。
- **P0-2 后端零类型检查**：无 tsconfig / typecheck 脚本，tsc 实测 72 错。Bun 运行时不校验类型，全部靠用户运行时踩雷。修复成本低（先加 tsconfig 把存量错误清零，再进 CI），收益极大，应是一切重构的**第一步护栏**。
- **P0-3 服务默认绑定 0.0.0.0 且无任何鉴权**：`Bun.serve`（server.ts:18135）未指定 hostname；`webServerJwtEnabled` 字段存在（server.ts:205）但**没有任何校验实现**（全文件无 verify/token 检查逻辑）。局域网内任何设备可直接 `GET /api/settings` 读走全部 API key、调用全部写接口。
- **P0-4 无 CORS/Origin 校验**：恶意网页可对 `http://localhost:8080/api/*` 发起跨站简单请求（POST JSON / GET SSE 不触发预检），等价于任意站点可读写本地配置与会话。
- **P0-5 `eval_javascript` 是进程内 eval 而非沙箱**（server.ts:8375-8390）：工具描述对模型声称 "QuickJS engine"，实际是 `new Function(...eval(code))`，仅以形参遮蔽 process/Bun/require；原型链/构造器逃逸可拿到完整宿主权限。与 P0-3/P0-4 组合意味着远程攻击面。

### P1（重要）

- **P1-1 持久化三轨制、三套自研可靠性机制并存**：state.json（原子写 + 8 重试 + 节流）、SQLite 活库（WAL + 脏标记 + 200ms flush + 损坏隔离重建）、memory/ JSON（串行写队列 + 启动重算不变式）。每轨单看工程质量都不错，但三套机制 = 三倍维护面，且互相之间有顺序耦合（迁移标记 `appliedMigrations` 决定 state.json 是否写 conversations/memories 字段，performStateSave server.ts:2690-2712）。`pc-data/` 中残留的多个 `state.json.*.tmp` 证明重试路径在真实环境被触发。
- **P1-2 全部会话常驻内存**：启动时 SQLite 全量加载进 `state.conversations`；`conversations/paged`、`conversations/search`（server.ts:16518-16545）都是内存线性扫描，搜索还是全消息体 `includes`。重度用户（代码注释自证存在 10GB+ 备份 zip 的用户）启动时间与内存占用无上界。
- **P1-3 fire-and-forget 生成链路**：发消息路由返回 202 后，OCR→生成→持久化在游离 async 块中运行（server.ts:16601-16610），错误只能靠 SSE 侧信道；`generateAnswer` 中 `completeConversationGeneration` 在成功、abort、错误、finally 四处调用（幂等掩盖控制流混乱，server.ts:15380-15425）。
- **P1-4 `updateSettings` 整体替换 `state.settings` 无并发隔离**（server.ts:15461）：流式生成期间读到的 `state.settings`、`state.conversations` 与用户改设置 / 删会话的写操作之间没有任何隔离或版本快照。多会话并发生成 + 用户中途改配置或删会话时，读到半更新状态属于设计层面允许发生的竞态，只是靠"改动够快、窗口够小"侥幸不暴露。
- **P1-5 三家 Provider 各写各的流式与工具循环**：OpenAI（fetchOpenAiTextStreaming，server.ts:13742）、Claude（streamClaudeChatWithTools + readClaudeStreamingRound，12222-12530）、Google（streamGoogleChatWithTools，12789-12898）三套独立实现，不存在统一的"流事件模型"。消息编码同样是三套（§2 第 14 项）。任何流式相关的 bug（工具边界、reasoning 增量、usage 统计、中断恢复）都要修三遍，且极易只修一处、另两处遗漏。
- **P1-6 `installProxyFetchInterceptor` 覆写 `globalThis.fetch`**（server.ts:2571）：全进程所有出站请求（provider、搜索、MCP、WebDAV、S3、models.dev、analytics、更新检查）都经过这一层。这是为绕开 Bun 的 env 快照锁不得不做的全局副作用；它有效，但意味着"网络"这一横切关注点被硬编码进全局，任何模块都无法在不受它影响的前提下发请求。

### P2（一般）

- **P2-1 122 处 `catch {}`**：多数是有意的 best-effort（清理临时文件等），但缺乏统一错误上报通道，部分静默吞错可能让用户看到"卡住"而非报错。
- **P2-2 `logs` 为纯内存态**（重启清空），统计另用 `RequestStats` 累加器持久化——两套并存是为对齐移动端行为，属可接受但需知晓的设计。
- **P2-3 端口顺延 + Tauri `RIKKAHUB_PORT:` 标记握手**：字符串协议耦合，脆弱但影响面小。

## 4. 前端审查（web-ui）

前端已配置 typecheck 且当前**通过**（实测 `react-router typegen && tsc` 无错），工程基线明显好于后端。但存在与后端同构的"巨型单体"问题：

### P1（重要）

- **FE-P1-1 `routes/settings.tsx` 9,407 行**：设置页把所有设置分区（Provider、模型、助手、搜索、MCP、备份、代理、字体、快捷键、记忆……）的表单、对话框、本地状态全塞在一个路由文件里。它与后端 106 个 `settings/*` 路由是一一镜像关系——后端设置逻辑的无边界，直接投射成前端设置 UI 的无边界。
- **FE-P1-2 类型人工同步、无单一事实源**：`web-ui/app/types/` 与后端 `server.ts` 各自定义 shape，靠人工保持一致（CLAUDE.md 明确承认"build 不会抓到 mismatch，只有运行时会"）。这是 §0"无接口契约"在前端侧的体现。
- **FE-P1-3 组件/数据流零测试**：145 个前端文件仅 3 个 `*.test.ts`（都是 lib 纯函数）。SSE 增量应用（applyNodeUpdate）、状态一致性等关键路径无测试。

### 数据流现状

- 设置全量推送：`GET /api/settings/stream` 每次推整份 `state.settings`（server.ts:2884 broadcastSettings），任一设置变更触发前端整份重渲染基线。记忆通道已独立拆出（memory SSE），是一次正确的"按变更频率分流"重构，可作为后续拆分范例。
- 会话增量：`node_update` 事件带整个增长中的 MessageNode（累积文本），后端已用 30fps 合并 + 显式治理过 SSE 连接风暴（broadcastNodeUpdateNow 的长注释 server.ts:2926-2948 记录了"每 chunk 触发 list invalidate → 耗尽 Chrome 6 连接上限 → 全部请求超时"的真实事故与修复）。这说明前端数据流的坑已被踩过并修过，是"资产"的一部分。

## 5. 备份与跨端兼容审查

这是**最不能推倒重来**的子系统，因为它是对外契约。

### 对外契约清单（重做/重构时必须逐字节保持不变）

1. **PC 备份 zip 结构**：`createSettingsBackupZipToPath`（server.ts:5429）产出的目录布局与 `applyPcBackupFromExtractDir`（3962）消费的布局必须对称；老版本导出的 zip 必须能被新版本导入。
2. **Android 互导契约**：
   - `generateRikkaHubDb`（server.ts:4711）为 Android 生成的 SQLite 必须匹配 Android Room 的 schema；已知 **FTS5 影子表**陷阱（dump schema 时影子表呈普通 CREATE TABLE，会泄露成孤儿表让 APP Room onOpen 重建虚拟表时崩溃，见用户记忆 backup-fts5-shadow-tables）。
   - **枚举域不可超界**：Android kotlinx.serialization 对未知枚举值不容忍，`ignoreUnknownKeys` 不救枚举（用户记忆 backup-android-enum-compat）。任何新增枚举值都会破坏 APP→PC→APP 往返。
   - **MemoryEntity 表**：APP 助手记忆在 `rikka_hub.db` 的 MemoryEntity 表而非 settings.json，APP→PC 导入必须单独读（用户记忆 backup-android-memory-table）。
   - **settings 七层合并方向**：APP→PC 的 settings 合并有固定优先级规则（用户记忆 backup-settings-merge-app-to-pc），不可随意改。
3. **pc-data 磁盘布局**：`state.json`（瘦身后字段集）、`rikka_hub.db`（pc_conversation / pc_message_node 表 + 迁移标记语义）、`memory/` 三 JSON、`files/`、`skills/`。迁移常量（如 `conversations-sqlite-1.2.6`、memory-file-split）是**诞生版本档案**，改了会让升级用户重复迁移（用户记忆 migration-id-is-birth-version）。

### 结论

备份子系统本身内聚度其实不低（相关函数集中在 3830-6180），**适合作为第一批被抽离成独立模块的对象**（`backup/pc.ts`、`backup/android.ts`、`backup/webdav.ts`、`backup/s3.ts`），抽离时行为零改动、以现有 smoke + 手动往返测试护住契约即可。它对"重做 vs 修复"的独立判断：**强烈倾向修复**——这里的每一条兼容规则都是单方面适配 Android（对方作者无合作意愿）踩雷换来的，重写没有对照物、极易回归。

## 6. 重做 vs 修复：最终权衡

### 判断：修复（渐进式模块化），不重做

| 维度 | 重做 | 修复（渐进模块化） |
|---|---|---|
| 实战边界修复的保全 | ✗ 数百个边界情况需重新踩雷 | ✓ 原样保留 |
| 跨端备份契约风险 | ✗ 无对照物，极易回归，伤害老用户 | ✓ 逐模块抽离，契约不动 |
| 单 exe 发布 | 需重建 | ✓ 不受影响（多文件照样 compile） |
| 风险粒度 | 一个巨型高风险切换 | ✓ 切成数十个可回滚小 commit |
| 见效速度 | 数月无可用产物 | ✓ 第一步（加 tsconfig）当天见效 |
| 处理的问题本质 | 把好逻辑连同烂结构一起扔 | ✓ 只给好逻辑补边界 |

**核心论点**：本项目面对的不是"烂逻辑"，而是"没有边界的好逻辑"。给好逻辑建立边界叫重构；重做会把好逻辑也一并丢弃、重新生成新的未知 bug。项目的真正价值沉淀在边界修复与跨端契约里，这两样都要求"保持行为不变地搬迁"，正是渐进重构的定义。

### 建议的分期路线（骨架，具体方案后续在本文档续写）

1. **阶段 0 · 建护栏（前置，必须先做）**
   - 为 `pc-server` 加 `tsconfig.json`，清零 72 个 tsc 错误，接入 `bun run typecheck` 与 CI。
   - 保留并强化 smoke 作为回归基线；补一个"备份往返"专项 smoke（PC→zip→PC、PC→APPdb→PC）锁死契约。
   - 此阶段不动任何架构，只让编译器和测试开始为后续搬迁保驾。

2. **阶段 1 · 按内聚度从高到低逐模块抽离**（每模块一个/一组 commit，行为零改动，抽完跑 typecheck + smoke）
   建议顺序（内聚度高、耦合少者先行）：
   1. 记忆存储层 → `memory-store.ts`（数据层已分离，代码搬迁最干净）
   2. 备份四件套 → `backup/*.ts`（内聚，契约明确）
   3. 文档解析 + 自制 ZIP/XML → `parsers/*.ts`（纯函数，无 state 依赖）
   4. 搜索服务 → `search/*.ts`（17 实现 + failover）
   5. 三家 Provider 客户端 → `providers/{openai,claude,google}.ts` + 一个统一流事件接口（这一步顺带解决 P1-5，是收益最大也最难的一步）
   6. TTS/ASR、字体、图标、代理各自成模块
   7. 路由表按领域拆分（`routes/settings.ts`、`routes/conversations.ts`……），最后 `server.ts` 只剩装配与启动。

3. **阶段 2 · 收敛横切关注点**

### 8.2 深审 A：推理引擎管线（P1-5 现状 = 解决约四成）

**已解决的部分（这是概念上最难的一半）**：`inference-engine/events.ts` 定义了统一的 `GenerationEvent` 判别联合（text_delta / reasoning_delta / image_delta / tool_call_created / tool_input_delta / tool_result / usage / finished / error / abort），且**已在生产主链路启用**——`runGeneration`（server.ts:3383）恒定注入 sink，经 `callProviderStreaming`（server.ts:2765）传给三家 provider；工具执行也已通过 `ToolExecutor` 接口注入，provider 层不再 import server.ts 的调度器（无循环依赖）。旧报告"不存在统一的流事件模型"的判断已部分过时。

**未解决的部分**：
1. **三套流循环仍独立并存**：`streamClaudeChatWithTools`（providers.ts:423）、`streamGoogleChatWithTools`（:814）、`fetchOpenAiTextStreaming`（:1654，另有 Responses API 变体 `readOpenAiResponseIntoMessage` :1609）各自持有一份完整的 `for (round < MAX_TOOL_STEPS)` 工具循环 + 各自的 SSE round 读取器（`readClaudeStreamingRound` :248 / `readGoogleStreamingRound` :701 / `readOpenAiStream` :1222）。工具循环的控制流（审批预扫、批量执行、消息回放、轮次上限）逻辑上是同一件事，实现了三遍。
2. **12 处 `if (hooks.sink) {...} else {...}` 双路径**：else 分支（直接改 `hooks.message`）在会话流式主链路是**死代码**（sink 恒存在），仅辅助调用（标题/翻译等无 hooks 场景）还走旧路。双路径让每个改动都要思考两条分支，是遗留搬迁态而非设计。
3. **四套消息编码仍在 server.ts**：`conversationMessagesForApi`（OpenAI chat）、`conversationResponseApiInput`（Responses API）、`claudeMessagesFromApiMessages`（blocks）、`buildGoogleRequestBody`（contents）。
4. **`inference-engine/providers/` 目录为空**——按 provider 拆文件的计划未执行。
5. **新增第 4 家 provider 的成本**：需要写全新的流读取器 + 工具循环 + 消息编码器，并同时改 `callProvider` 与 `callProviderStreaming` 两处 if/else 分发。不存在 Provider 接口/注册表。

**结论**：P1-5 的收敛路径已经清晰且低风险——事件模型已验证可用，下一步是把"工具循环"上提为一个共享的驱动器（provider 只实现「发一轮请求 + 把响应流翻译成 GenerationEvent + 提供消息回放编码」三个钩子），随后删除 12 处死分支。此项列为阶段 7（见 8.6）。

### 8.3 深审 B：持久化与鲁棒性（P1-1/2/4 全部原样存在，但实现质量高于预期）

- **P1-1 三轨制原样**：state.json（persistence/json-store.ts，原子写 temp+rename + 8 次退避重试 + recovery 兜底 + 200ms 节流 + 在途合并）、SQLite 活库（conversations/index.ts，WAL + 脏标记 + 200ms 节流 flush + 删除竞态防护）、memory/（串行写队列）。**顺序耦合仍在**：`performStateSave` 依据 `appliedMigrations` 标记决定是否落 conversations/memories 字段（json-store.ts:53-63）——正确但脆弱，是"必须读注释才能安全修改"的典型。
- **P1-2 全量常驻确认**：启动时 `loadAllConversationsFromDb`（conversations/index.ts:98）把**所有会话的所有 message node** 载入内存（每会话一次 node 查询 + 每节点 JSON.parse）；`conversations/paged` 与 `conversations/search`（api/handlers/conversations.ts:66-88）都是对 `state.conversations` 的线性扫描，search 是全消息体小写 `includes`，无索引（PC 表没有 FTS）。10GB 级备份的重度用户（代码注释自证存在）启动时间与常驻内存无上界。

### 8.4 深审 C：前端数据流（质量整体尚可，一个结构性缺口）

- **N-8（新发现）SSE 断线重连不一致**：`services/api.ts` 的 `sse()` 读取器**本身不重连**，四路订阅各自为政——memory-store 自带指数退避重连（1s→30s，注释自证"sse() 本身不自动重连"）；settings 订阅 onError 只补拉一次快照，流死了不再恢复；会话列表订阅只 console.error；会话详情靠"仅在 isGenerating 时的 10s 轮询"兜底。**后果**：改端口/重启服务器/网络抖动一次，除记忆外的所有实时通道静默失联，UI 看起来正常但不再更新，直到用户手动刷新页面。修复形状：把 memory-store 的退避重连下沉进 `sse()` 本体（带 abort 透传），四路订阅同时受益。
