# 专题3:数据备份 全链路研究(2026-07-28)

## 一、问题定义

三条备份路径:PC→PC、PC→APP、APP→PC。用户长期反馈:偶发导入失败、导入后部分信息
丢失(典型:头像)、1.4.1 导出 zip 内同一附件恰好出现四次。本轮以安卓仓库最新源码
(2.4.3,Room schema v24,2026-07-28)为基准,对 PC 备份模块(pc-server/backup/ 四文件
约 2900 行 + api/handlers/data.ts + 前端 data.tsx)与安卓备份实现(WebDavSync/S3Sync/
SettingsJsonMigrator/Room 实体)做了逐契约点对照,并对可疑点做了本机实测。

## 二、核心结论(一句话)

**PC↔PC 路径经备份 2.0 重构后基本健康;PC→APP 路径存在一个"全附件静默丢失"的载体级
P0(Windows zip 反斜杠)和三个"整包恢复失败/会话打不开"的契约级 P0;APP→PC 路径的头像
丢失是 settings 内 URL 双向都不改写造成的;另有三项结构性欠账(模板依赖/表清空/字段改名)。**

全部修复都在 PC 侧完成,无需安卓端配合。

## 四、Z-1:Windows zip 反斜杠(P0,本机实测证实)

### 证据
`backup/export.ts` Windows 分支用 PowerShell `[ZipFile]::CreateFromDirectory` 打包。
本机实测(Windows PowerShell 5.1 / .NET Framework):**条目名为 `upload\a.txt`(反斜杠)**。
安卓恢复端(WebDavSync.restoreFromBackupFile)逐条目判断
`zipEntry.name.startsWith("upload/")` / `"skills/"` / `"fonts/"` —— 反斜杠条目全部不命中,
走 else 分支 `Log.i("Skipping entry …")` **静默跳过**。顶层无分隔符的 settings.json 与
rikka_hub.db 正常恢复。

### 用户可见后果
- PC(Windows)→APP:会话文本在、**所有图片/文档附件字节缺失(全裂图)**、skills 全丢、fonts 全丢。
  与用户"导入后部分信息丢失"的反馈精确吻合——这是损害面最大的一条。
- PC(Windows)→PC(Linux/Docker):`unzip` 在 Linux 把反斜杠当作文件名字符,解出的是名为
  `upload\a.txt` 的顶层文件,`extracted/upload/` 目录不存在 → 附件同样全丢。
- PC(Windows)→PC(Windows) 不受影响(Expand-Archive/ExtractToDirectory 兼容反斜杠),
  这正是现有冒烟全绿却漏掉此病的原因。

### 终极方案
打包器换 Windows 自带 bsdtar(`C:\Windows\System32\tar.exe`,Win10 1803+ 必有;应用基线
WebView2/Win10 已高于此):`tar.exe -a -c -f <zip> -C <stage> <顶层条目…>`。
本机实测产物条目为 `upload/a.txt`(正斜杠,零 `./` 前缀,安卓端逐前缀命中)。
注意必须显式枚举顶层条目而非 `.`(`.` 会产生 `./upload/…` 前缀,同样不命中)。
兜底:tar.exe 缺失时回退 PowerShell,随后对 zip 做一次字节级归一化(local header 与
central directory 的 name 字段内 0x5C→0x2F;文件名长度不变,偏移全部不动,零风险),
两条路径产物一致。冒烟新增"zip 条目名不含反斜杠且 upload/ 前缀精确"断言。

## 五、A 族:PC→APP 消息/设置的 kotlinx 严格解码破绽(P0)

安卓 `JsonInstant` 配置为 `ignoreUnknownKeys=true`(多余字段安全),但三类形状错误必炸,
且炸点无容错:settings 在 restoreFromBackupFile 中 throw → **整包恢复失败**;会话在
ConversationRepository.loadMessageNodes 中 decode 无 try-catch → **该会话永远打不开**。

### A-1 预设消息形状(settings 整包失败)
PC 端预设消息创建为 `{ role: "ASSISTANT", content: "" }`(web-ui assistants.tsx),而安卓
`Assistant.presetMessages: List<UIMessage>` 的 **parts 无默认值、必填**。
导出批6只做了 role 小写化,没有做形状转换 → 任何在 PC 配过预设消息的用户,PC→APP 恢复
settings 时 `Failed to restore settings` 整包失败。这是"偶尔有用户导入失败"最有力的解释
(触发条件:配置过预设消息;不触发的用户完全正常,呈"偶发"观感)。
PC 自身兼容双形状(helpers.ts partsFromPreset 同时接受 content/parts)。
**方案**:导出时把 preset 归一化为完整 UIMessage 形状——
`{ id: uuid, role: 小写, parts: [{type:"text",text:content}] }`(createdAt 可省略,安卓有默认);
已是 parts 形状的原样透传。PC 导入方向无需改(partsFromPreset 已兼容)。

### A-2 model_call_error 注解(单会话打不开)
`conversations/orchestrator.ts:663` 生成失败时向消息 push
`{ type: "model_call_error", message }` 注解;安卓 `UIMessageAnnotation` 密封类**只有
url_citation**,未知判别符 SerializationException,loadMessageNodes 无容错 → 含任何一次
生成失败记录的会话,导到 APP 后点开即崩/空。
**方案**:导出 rikka_hub.db 时(fixParts 同层)按白名单过滤 annotations,只放行
url_citation;PC 原生 dump(pc_conversations.db)不动,PC→PC 零损。

### S-1 custom_js 搜索服务(settings 整包失败)
安卓 SearchServiceOptions 判别符全集:bing_local/zhipu/tavily/exa/searxng/linkup/brave/
metaso/ollama/perplexity/firecrawl/jina/bocha/rikkahub/grok/tinyfish——**无 custom_js**。
PC 用户配置了自定义 JS 搜索服务后,PC→APP settings 恢复整包失败。
**方案**:导出 settings.json 时过滤掉 type 为安卓不识别的搜索服务(白名单以安卓全集为准,
硬编码+注释锚定安卓源文件);pc-backup.json 保留全量,PC→PC 无损。TTS/ASR/providers/
localTools 判别符已逐一对照,两端一致,无需处理。

### E-1 消息 id 显式 null(边缘)
insertConversationsIntoDb 写 `id: m.id || null`;安卓 `UIMessage.id: Uuid`(非空,有默认)
遇 JSON 显式 null 必炸(kotlinx 对非空属性的 null 不因默认值而豁免)。PC 消息实践上都有 id,
属边缘,但顺手修:缺失时 `Bun.randomUUIDv7()`,绝不写 null。

## 六、H-1:头像双向丢失(P0,用户反馈直接对应)

附件字节本身两个方向都在 zip 的 upload/ 里(PC 引用扫描含 settings 全量,安卓头像也存
upload/),**丢的只是 URL 指向**:

- **PC→APP**:导出批6只把消息节点 JSON 里的 `/api/files/<id>/content` 反写成安卓 upload URI,
  **settings.json 里的头像 URL(助手头像/用户头像,file-refs.ts 注释明确"助手头像均是
  /api/files/<id>/content")原样带出** → 安卓拿到相对路径,Coil 加载失败,头像丢失。
- **APP→PC**:导入侧 rewriteAndroidFileUrlsDeep 只作用于会话消息;settings 七层合并接受了
  APP 的 userAvatar/助手 avatar,但 `file:///data/user/0/…/upload/<name>` **不改写** →
  前端 resolveFileUrl 把它转成 `/api/files/path/upload/<name>`,而**该端点在后端根本不存在**
  (全仓 rg 零命中,W-1 死分支)→ 必 404,头像丢失。

**方案**(复用现有机制,对称补齐):
- 导出:rewritePcUrlsToAndroidUpload 同样作用于 settings.json 文本(id→backupName 映射已有)。
- 导入(安卓 zip 路径):settings 合并完成后,对 state.settings 跑 rewriteAndroidFileUrlsDeep
  (androidFilenameToPcId 映射已有,时序上文件注册先于会话导入,只需把 settings 改写挪到
  注册之后——现状 settings 合并在文件注册之前,需调整顺序或补一次后置改写)。
- 前端 W-1:后端改写彻底后,file:// 分支成为真死代码,删除(或指向 404 的 path 端点一并清理)。

## 七、T 族:rikka_hub.db 的模板依赖与表清空(P1,结构性)

### 现状
PC 生成安卓格式库的 schema 来自 `rikka_hub_cached.db`——上一次成功导入安卓备份时缓存的
整库副本。两个结构性缺陷:

- **T-1 无模板则无会话**:纯 PC 用户(从未导入过安卓备份)导出的 zip 不含 rikka_hub.db,
  导到 APP 会话为空,只有一条 warn 日志。"PC 能否导给 APP"取决于"是否曾从 APP 导入过",
  用户不可理解。
- **T-2 非 PC 管理的表被清空**:重建时只灌 ConversationEntity/message_node/MemoryEntity,
  其余表(workspaces/favorites/conversation_folder/GenMediaEntity/managed_files)空表出场;
  ConversationEntity 的新列(mode_injection_ids/lorebook_ids/workspace_cwd/folder_id,
  v19→v24 增量)PC 不认识,恢复为默认值。APP→PC→APP 往返 = 手机上的文件夹分组、收藏、
  工作区、生图画廊、会话级世界书/模式注入绑定**全部清零**。

### 终极方案
- **T-1**:把安卓仓库 `app/schemas/…/24.json`(Room 官方 schema 快照,含每张表的 createSql、
  identityHash、版本号)vendor 进 PC 仓库,导出时无模板则从 schema JSON 直接生成全新 v24 库
  (含 room_master_table 的 identity_hash 与 android_metadata)。安卓 Room 迁移链 1→24 完整
  (AppDatabase.kt 全部登记),旧 APP 收到新库走不了、新 APP 收到旧库自动迁移——vendored
  版本随每次"安卓对齐批次"更新即可。模板存在且版本≥vendored 时仍优先模板(保留 T-2 的数据)。
- **T-2**:重建策略从"空库+灌两张表"改为"cached.db 整库拷贝为基底,只 DELETE+重灌 PC 管理的
  三张表(ConversationEntity/message_node/MemoryEntity),其余表原样保留";且重灌
  ConversationEntity 时,同 id 会话的 PC 不认识列(folder_id 等)从 cached 行原值回填。
  数据新鲜度:非 PC 管理的表停留在"上次 APP→PC 导入时刻"——恢复本就是替换语义,比清空
  严格更优,且对未来安卓新增表/新增列**自动前向兼容**(这是该设计的核心价值)。
  FTS 虚拟表与影子表的既有排除逻辑保持不变。

## 八、F-1:contextMessageSize → contextMessageLimit 改名漂移(P1)

安卓 2026-07-25(b0698524)删除 `contextMessageSize`,07-28(2d61ba95)新增
`contextMessageLimit`(语义升级为阶梯式截断,保提示词缓存)。PC 全链(类型/默认值/
conversation-encoding 切片)仍用旧名。后果:双向迁移后"上下文条数限制"静默回到"不限制"。
**方案**:PC 跟进改名(类型+默认值+编码层+设置 UI),normalizeState 做一次性迁移
(旧字段存在且新字段缺失 → 取旧值,删旧字段);导入侧两名兼容读。PC 的切片语义与安卓
阶梯截断的差异属于推理引擎对齐话题,不在备份专题内展开,备份层先保证字段不丢。

## 九、历史疑案收口:附件恰好四次(1.4.1)

机制已闭环,无需新修复:1.4.1 的安卓 zip 导入路径把 upload/ 全量追加注册进 state.files
(无内容去重),每次 PC↔APP 往返翻一倍,两轮=4 份,与用户"恰好四次"吻合;导出侧当时

文件复用 id;导出按内容去重共享 zip 内文件名。存量脏数据自愈:带 4 份重复的老库再导出,
zip 只含 1 份;再导入,4 个旧 id 全部映射到同一新 id,引用改写后归并为 1 条。已有回归卫
(smoke 的去重断言)。
