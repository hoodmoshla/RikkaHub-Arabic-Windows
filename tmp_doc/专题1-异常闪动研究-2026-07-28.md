# 专题 1:异常闪动 —— 源码级归因研究

日期:2026-07-28 | 范围:web-ui 全渲染链路 + pc-server 推送侧 | 状态:研究完成,待决策修复

## 〇、结论速览

用户报告的五类闪动,静态源码分析归因为 **四个病根家族**。它们不是同一个 bug,但 A 族(默认值首帧)覆盖了其中三类症状,是最大的一族:

| # | 症状 | 病根家族 | 归因确定度 |
|---|------|---------|-----------|
| 1 | 启动时:默认头像/昵称→闪→真实值;列表空→闪→加载;侧边栏突然变宽 | **A. 默认值首帧** | 实锤(逐条对上) |
| 2 | 切换会话:瞬间显示中间/开头位置;轮次条先指第 1 轮再跳末轮 | **C. 虚拟列表挂载稳定期** | 实锤(轮次条机制完全对上) |
| 3 | 设置页切回主界面:左侧边栏闪一下 | **B. 路由重挂载 + 假动画** | 实锤 |
| 4 | 设置子板块切换:数据板块瞬间"卡片式展开"再恢复 | **A. 默认值首帧**(板块内异步查询) | 实锤(data.tsx:660) |
| 5 | 流式输出时整个界面不平滑/闪动 | **D. 流式重渲染面过大** | 高置信(多个放大器叠加) |

大规模数据(百千会话/数千轮对话)会**显著放大** C、D 两族,详见第六节。

## 一、病根家族 A:默认值首帧(render-then-fetch,无本地镜像)

### 机理

本应用是纯 SPA + 服务端单一数据源:所有"用户状态"(settings、会话列表、各板块状态)都在**挂载后异步到达**。而首帧一律先用**内置默认值/空值**渲染,数据到达后跳变。用户看到的每一次"闪",就是一次"默认值帧 → 真实值帧"的突变。商业级应用(Slack/Discord/ChatGPT 桌面端)对此的标准做法是**本地快照镜像(stale-while-revalidate)**:上次会话的状态同步落在本地,首帧直接画"上次的真实值",服务端数据到达后静默校正——绝大多数情况下两者一致,零视觉跳变。

### 证据链

**A1. settings 无任何本地持久化**(`app/stores/slices/settings-slice.ts`,全文 8 行):

```5:8:web-ui/app/stores/slices/settings-slice.ts
export const createSettingsSlice: StateCreator<AppStoreState, [], [], SettingsSlice> = (set) => ({
  settings: null,
  setSettings: (settings) => set({ settings }),
});
```

settings 唯一来源是 `/api/events` SSE 快照,路径:React 挂载 → SharedWorker 构造(脚本加载+编译)→ SSE 连接 → 服务端推 settings 快照 → postMessage 回页面 → store 填充。这条链路有数十至数百 ms,期间:

- 侧边栏用户名/头像渲染默认值(`conversations.tsx:1858-1861`:`settings?.displaySetting` 为 null 时兜底);
- 所有依赖 settings 的 UI 均为默认态。

**A2. 界面缩放在 settings 到达后才生效 → 布局整体跳变**(`root.tsx:162-170`):

`--rikkahub-ui-scale` 写在 `AppContent` 的 useEffect 里,依赖 `displaySetting.uiFontSize`。而根字号规则(`app.css:1136`)是 `font-size: calc(16px * var(--rikkahub-ui-scale, 1))`,侧边栏宽度是 `16rem`(`ui/sidebar.tsx:30`)。**只要用户设置过非 1 的界面字号,首帧按 16px 画(侧边栏 256px),快照到达后根字号突变,全部 rem 布局集体跳一档**——"侧边栏突然变宽一点"就是它,而且不止侧边栏,是整个界面同时缩放,视觉上就是"闪一下"。

**A3. 会话列表无缓存,每次挂载从零加载**(`use-conversation-list.ts:49-51`):

```49:51:web-ui/app/hooks/use-conversation-list.ts
  const [conversations, setConversations] = React.useState<ConversationListDto[]>([]);
  const [activeId, setActiveId] = React.useState<string | null>(routeId ?? null);
  const [loading, setLoading] = React.useState(true);
```

对比:会话**详情**已有模块级 `detailCache`(批次修复时加的,`conversations.tsx:418`),切换会话零加载态;但会话**列表**没有对应机制。启动时"列表空 → 闪 → 加载出来"、以及症状 3 的列表重取,都源于此。

**A4. 设置子板块内的异步查询首帧**(症状 4 实锤,`settings/data.tsx`):

```67:67:web-ui/app/components/settings/data.tsx
  const [schemaExpanded, setSchemaExpanded] = React.useState(false);
```

```660:660:web-ui/app/components/settings/data.tsx
        {(!schemaStatus?.hasAndroidSchema || schemaExpanded) && (
```

`schemaStatus` 初值 `null`(挂载后才 GET)。首帧 `!schemaStatus?.hasAndroidSchema === true` → "安卓兼容"卡片按**未注册态全展开**渲染(琥珀色徽章 + 上传表单,占一大块),查询返回 `hasAndroidSchema: true` 后收起为一行摘要。这正是"闪动瞬间手机端适配的卡片式展开的,闪动完恢复"——其实不是手机端布局,是未注册态的展开表单,视觉上像一叠卡片。其它板块"看不清闪了什么"的,属同族:板块挂载 → 异步取数(logs/stats/webdav 列表等)→ 内容二次跳变,叠加 ScrollArea 滚动位置重置。

### 启动闪动的完整时序(用户观察 vs 代码)

1. HTML/JS 加载 → `HydrateFallback` 三点跳动;
2. React 挂载:默认头像/昵称、空列表、根字号 16px ←— 用户看到的"默认值帧";
3. 会话列表 GET 返回 → 列表出现(**闪 1**);
4. SharedWorker→SSE→settings 快照到达 → 头像/昵称换真实值 + 根字号突变 → 整体布局跳变(**闪 2**,含"侧边栏变宽");
5. 自定义字体 @font-face 加载完成 → 字形替换(轻微,FontFaceInjector)。

三次可感知跳变,顺序不定(取决于网络/调度),所以"有时候闪一下、有时候闪两下"。

## 二、病根家族 B:路由级重挂载 + 假动画(症状 3)

### B1. PageTransition 的动画是"假"的(`root.tsx:118-136`)

```122:134:web-ui/app/root.tsx
  return (
    <AnimatePresence mode="wait" initial={false}>
      <motion.div
        key={pageKey}
        initial={{ opacity: 0, y: 8 }}
        animate={{ opacity: 1, y: 0 }}
        exit={{ opacity: 0, y: -4 }}
        transition={{ duration: 0.25, ease: [0.16, 1, 0.3, 1] }}
        className="contents"
      >
```

`className="contents"` = `display: contents`——该元素**不生成盒子**,CSS 规定 opacity/transform 对其**不产生任何视觉效果**。所以这段"淡入淡出+位移"的过渡动画实际渲染效果是:**旧页面原样停留 250ms(exit 动画在 JS 里空跑)→ 硬切到新页面(enter 动画同样不可见)**。用户感知就是"顿一下然后闪一下"。`display: contents` 的选择本身有原因(避免包一层 div 破坏 h-svh/flex 布局链),但它让整个过渡设计形同虚设。

### B2. chat↔settings 切换 = 聊天路由整棵卸载重挂

`AnimatePresence mode="wait"` + `key=getTopLevelPageKey(...)`:从设置返回时,conversations 路由**全新挂载**:

- `useConversationList` 回到 `[] + loading:true` → 侧边栏先渲染"加载中"空列表,GET 返回后再填充(**这就是"左侧边栏闪了一下"**);
- 会话详情靠 `detailCache` 命中所以消息区基本无感——侧边栏没有对应缓存,所以只有它闪。

同一帧内"硬切 + 侧边栏空列表 → 填充"两次跳变叠加,就是症状 3。

## 三、病根家族 C:虚拟列表挂载稳定期(症状 2)

切换会话时 `<Virtuoso key={activeId}>` 强制重挂载(`conversations.tsx:1045`),`initialTopMostItemIndex` 已让首帧渲染在末尾(此前批次的修复,方向正确)。残余闪动来自挂载后的**测量稳定期**:

**C1. 变高条目测量修正**。Virtuoso 首帧用估算高度渲染 `initialTopMostItemIndex` 附近的条目,真实高度(长消息/代码块/图片)测量后窗口位置修正,可见内容瞬间平移——"瞬间显示的似乎是中间位置"。会话越大、消息越高越明显。未设置 `defaultItemHeight`,估算与真实差距大时修正幅度大。

**C2. 轮次条初值机制(完全实锤)**。`conversations.tsx:1160-1166`:

```1160:1166:web-ui/app/routes/conversations.tsx
                activeIndex={
                  isAtBottom
                    ? selectedNodeMessages.length - 1
                    : isAtTop
                      ? 0
                      : Math.round((topVisibleIndex + topEndIndex) / 2)
                }
```

- `isAtBottom` 初值 true(`:872`),但 Virtuoso 挂载稳定期会先回调 `atBottomStateChange(false)`;
- 此时 `topVisibleIndex`/`topEndIndex` 还是初值 0(`:874-875`,要等第一次 `rangeChanged`)→ activeIndex 算出 **0 = 第 1 轮**;
- 稳定后 atBottom(true)/rangeChanged 到位 → 跳回末轮。

**"轮次条刚进来瞬间指向第一轮,闪动后指向最后一轮"逐帧对上。** 同机制还让"回到底部"按钮(`!isAtBottom` 时显示)在切换瞬间闪现一下。

**C3. 未命中缓存的会话**:detailCache 未命中 → 首帧空白(≤250ms 不出加载文案,`:943-953` 设计合理)→ SSE 快照到达整屏出现。小会话无感;大会话见第六节。

## 四、病根家族 D:流式重渲染面过大(症状 5)

服务端已做对的事:node_update 33ms 节流、流式期间**不**广播列表失效(`pc-server/api/sse.ts:218-233` 有完整教训注释)。问题在前端每个 chunk 的重渲染波及面:

**D1. 每 chunk 重建会话列表数组**。`useConversationDetail` 每个 node_update 调 `updateSummary`(`conversations.tsx:506`),而 `updateConversationSummary`(`use-conversation-list.ts:92-112`)**无条件** `.map` 重建全数组 + 重排序——`updateAt` 每 chunk 都变,短路不了。结果:整个侧边栏组件树每 33ms 重渲染一次(行级 memo 只救了非活跃行)。

**D2. 轮次条每 chunk 全量重建**。`conversations.tsx:1155-1159`:`items` 在 JSX 里**内联** map 构建(新数组 + 每条算 preview),父组件每次重渲染(= 每 chunk)全部轮次条条目重渲染。每条还包一个 Radix `Tooltip`(带 context/state 的真组件,`conversation-quick-jump.tsx:104`)——百轮会话即数百个 Tooltip 实例参与 30Hz 重渲染。

**D3. followOutput="smooth"**(`:1051`):每 chunk 触发一次平滑滚动动画,连续 chunk 下动画不断重启,与内容增高的测量修正叠加,产生"抖/滑不动/跳"的观感。

**D4. markdown 预处理全文正则**。`markdown.tsx:130`:`preProcess(content)` 对**整段增长中的文本**跑多个全局正则(代码块定位 + LaTeX 转换),每 chunk 一遍,单条消息流到几十 KB 时是 O(n²) 累积。Streamdown 本身的块级 memo 是对的,但预处理在它上游。

**D5. 布局层面**:消息区没有 `overflow-anchor`/`contain` 类的滚动锚定加固,代码块从"无高亮→Shiki 高亮"(首次语言异步加载,`code-block.tsx:250-259`)有一次替换,流式中新代码块会闪一次色。

## 五、为什么"重构之后"才明显?

重构本身没有引入新 bug,但两件事让老问题浮出水面:
1. 单通道化(SharedWorker + /api/events)把 settings 从"页面直连 SSE"变成"worker 中转",首快照到达略晚于旧架构,默认值帧窗口拉长,启动闪动更易被看见;
2. 批次修复砍掉了冗余 GET、加了 detailCache,**消息区**变快了——衬托出侧边栏/设置/轮次条这些没有缓存治理的部位,跳变反而更显眼。

## 六、大规模数据放大效应(百千会话 / 数千轮对话)

| 场景 | 现状行为 | 放大后果 |
|------|---------|---------|
| 数千轮会话:打开/切换 | SSE 连接即推**全量会话 JSON**(所有节点+所有分支+所有 parts) | 传输+JSON.parse 数 MB~数十 MB,主线程停顿;空白期远超 250ms,"加载中"常驻;detailCache 留 20 个大对象,内存驻留可观 |
| 数千轮会话:轮次条 | 全量渲染,每轮一个 Radix Tooltip,无虚拟化 | 数千个 Tooltip 实例:挂载卡顿数百 ms,流式期间 30Hz 重渲染这数千个组件,就是"一直卡着一直闪" |
| 数千轮会话:Virtuoso 挂载 | 估算高度稳定期 | 条目越多、高度方差越大,首帧位置修正越明显 |
| 数千轮会话:流式 | preProcess 全文正则/chunk | 消息越长每 chunk 越贵,后期打字肉眼变卡 |
| 成百上千会话:列表 | 分页 30/页 + loadMore,失效刷新 ≤100 条 | **有界,基本健康**;侧边栏行未虚拟化,用户手动滚很深后 DOM 变大,属次要 |
| 流式期间列表 | 每 chunk 重建数组+排序(D1) | 会话列表越长,每 33ms 的 map+sort 越贵 |

结论:你的担忧成立。轻度用户看到的是"闪一下",重度用户(千轮会话)会遭遇**秒级白屏 + 持续卡顿**,C/D 两族在他们身上是质变。

## 七、修复方案建议(按根源性排序,待决策)

### P0-1|本地状态镜像(治 A 族,启动/设置板块闪动的终极解)
- settings 落 localStorage 镜像(只作**只读缓存**,权威仍是服务端快照,到达即覆盖;不回写,无数据安全风险);store 初值同步读镜像 → 首帧即上次真实值;
- `--rikkahub-ui-scale`/字体族改为 `<head>` 内联脚本预绘制(与主题防 FOUC 同模式):首帧根字号就是正确值,**彻底消灭布局跳变**;
- 会话列表首页同样镜像(或模块级缓存,与 detailCache 同思路):启动/返回首帧画上次列表,GET 返回静默校正;
- `schemaStatus` 等板块内异步态:未知时**不渲染表单**(保守骨架占位)或模块级缓存上次结果。

### P0-2|路由过渡治理(治 B 族)
- 修 PageTransition:去掉 `display: contents` 换真实动画容器(需处理布局链),**或**承认硬切、把 250ms 空等撤掉;
- chat 路由保活(settings 覆盖式渲染或缓存路由状态),至少让列表 hook 状态在返回时不清零——配合 P0-1 的列表镜像,重挂也无感。

### P1-1|切换会话首帧治理(治 C 族)
- `isAtBottom`/`topVisibleIndex`/`topEndIndex` 随 `key=activeId` 一起按 initialLocation 播种初值(轮次条首帧就指末轮);Virtuoso 稳定前忽略 `atBottomStateChange(false)`,"回到底部"按钮不再闪现;
- 设 `defaultItemHeight` 收窄估算差;
- 轮次条:items 提为 useMemo;Tooltip 惰性化(悬停才挂 content)或超过阈值(如 200 轮)降采样/虚拟化。

### P1-2|流式渲染面收敛(治 D 族)
- `updateConversationSummary` 短路:展示字段(title/isPinned/isGenerating/分钟级 updateAt)不变则不 setState;
- 轮次条 items memo(同 P1-1);
- `followOutput` 流式期间改 `"auto"`(瞬时贴底,不重启动画);
- preProcess 增量化或按块缓存(可后置,收益随消息长度增长)。

### P2|大会话专项(重度用户质变问题,建议独立专题)
- 会话快照分页/窗口化(SSE 首帧只推尾部 N 轮 + 按需回溯),根治数十 MB 全量快照;
- detailCache 按消息数加权限容。

### 验证方案
修复前后各录一组:DevTools Performance(启动/切换/流式 30s)+ React Profiler(流式期间 commit 次数与波及组件数)+ 慢动作录屏(240fps 手机拍启动/切换)。用 1000 轮合成会话与 500 条会话列表做放大试验。
