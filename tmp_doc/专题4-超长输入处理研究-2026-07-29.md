## 一、现状事实(两端源码核实,均带出处)

### 1.1 PC 端文件链路
- 上传:`POST /api/files`(api/handlers/files.ts)→ 字节落盘 `pc-data/upload/` → `state.files` 登记(id/文件名/mime/大小)。HTTP 体积上限 64GB(server.ts maxRequestBodySize),等于不设防。
- **文档提取在上传请求内同步完成**(files.ts 在响应前调 extractStoredFileText 并打日志)——这是现状真毛病:大文件上传转圈会卡到提取结束(专题4 要改成后台)。
- 提取结果写旁车缓存 `pc-data/extracted-text/<id>.txt`(files/index.ts extractedTextPath),**只提取一次**,编码热路径只读旁车(1-7/3-4 纪律)。空结果进程内负缓存,不落盘(R4-4)。
- 提取器(files/index.ts extractNonPdfText / extractPdfText):
  - PDF:mupdf-wasm(9.6MB wasm 经 `with {type:"file"}` 嵌进单 exe),**现状 buffer-only**:`readFileSync` 全量进内存再 `Document.openDocument(buf)`,故有 `MAX_PDF_EXTRACT_BYTES = 100MB` 上限,超限走兜底文案。逐页 `loadPage(i).toStructuredText()`,页间 setImmediate 让出事件环(R4-3)。
  - DOCX/PPTX/EPUB:**已是流式**——files/zip-file.ts 中央目录随机访问读取器(对齐安卓 java.util.zip.ZipFile 语义,打开只读 EOCD+中央目录,条目按需解压,zip64 支持),**无大小上限**。塞满图片的 500MB PPTX 峰值内存 = 单个 slide XML。
  - 纯文本/代码文件:mime `text/*` 或扩展名白名单(txt/md/markdown/csv/tsv/json/jsonl/yaml/yml/xml/html/css/js/ts/py/…)全量 utf8 读入,`MAX_TEXT_EXTRACT_BYTES = 100MB` 上限(**保留**:100MB 文本≈2500万 token,无模型可食,此上限保护的是常识而非内存)。
- 消息构建(inference-engine/message-builder.ts):document part → 读旁车全文 → `documentPromptText`(`## user sent a file: <名>` + 代码块)注入,**全文、不分块、不截断**;旁车未就绪 → `fallbackDocumentText` 降级 + `ensureExtractedTextAsync` 后台补抽,下轮生效。
- 图片:原样存盘;发送时读盘转 base64 data URL;目标模型无 IMAGE 模态时用辅助模型 OCR(conversations/auxiliary.ts,结果存 part `metadata.ocrText`)以 `<image_file_ocr>` 文本替代(对齐安卓 OcrTransformer)。
- 前端 accept 清单(web-ui/app/lib/upload.ts `DOCUMENT_UPLOAD_ACCEPT`):txt/md/markdown/csv/tsv/json/yaml/yml/pdf/doc/docx/xls/xlsx/ppt/pptx/epub。**txt/md 本来就支持,端到端通**(用户原以为不支持,已核实为非问题)。
  - ⚠️ 瑕疵:清单含 legacy Office(.doc/.xls/.ppt/.xlsx?),后端**无**这些二进制老格式解析器,传了只有兜底文案 → 误导,实施时清理。

### 1.2 APP 端(安卓)对照
- `DocumentAsPromptTransformer`(data/ai/transformers/):**每次发请求都从磁盘重新解析文档**(无缓存,PC 的旁车方案更优),原生 MuPDF(com.artifex.mupdf.fitz)按路径打开、库内流式读页,DOCX/PPTX/EPUB 自研解析器(document 模块)。全文包成 `<UploadFile name="..." path="...">` 文本 part 插到消息最前(注:插最前对 provider prompt cache 更友好)。
- 解析与注入**无任何字节/字符上限**(transformers 目录无 take/substring/maxLength)。
- 长文本:输入框无上限;`pasteLongTextAsFile`(默认关)+ `pasteLongTextThreshold`(默认 1000),安卓在通用设置页**有 UI**(SettingPreferencesGeneralPage)。
- 历史截断:仅 `contextMessageLimit` 按消息条数阶梯截断(GenerationHandler),不按 token。

### 1.3 共同结论
两端对超长输入的现状 = **入口不设防、中间不瘦身、出口靠模型报错**(provider 400 原样透传)。真正的上限从来在模型上下文窗口。经与用户讨论确认:主流成熟产品(ChatGPT 等)同样是发后报错、不做发前硬拦截,故**不做发送前预警**;要做的是报错人话化(见方案③)。

## 二、核心研究结论:PDF 流式解析(终极解,已验证 API 真实性)

### 2.1 为什么不换库(跳出框架评估过)
- pdf.js:纯 JS 无 wasm 堆天花板,但**中文提取依赖约 180 个 CMap 资产文件**(单 exe 打包痛,缺了中文乱码,用户以中文为主),提取顺序质量不如 MuPDF 结构化文本,速度慢。
- PDFium wasm:同样 buffer-only,换了白换。
- 原生库/外带 mutool:与 `bun build --compile` 单 exe 分发不兼容。
- provider 原生文档输入(Claude/Gemini/OpenAI 文档模态):未来可做的**新功能方向**(provider 级解析+扫描件 OCR),但只覆盖部分 provider、按页计费、文件出设备,非本地提取替代品。
- **结论:留 mupdf-wasm**。与安卓同库 → 同文件两端提取逐字一致;中文 CMap 内置零配置;质量业界最好。问题从来不在库,在运行方式。

### 2.2 流式打开(mupdf.js 1.27 Stream API,已读源码验证)
- `Document.openDocument(from: Buffer | ... | Stream | string, magic)`;`new Stream(handle)` → wasm 内建原生 `fz_stream`,读/寻址回调进 JS:
  - `$libmupdf_stm_read(id, pos, addr, size)` → `handle.read(libmupdf.HEAPU8, addr, size, pos)`(**直接把文件字节读进 wasm 堆窗口**,用 `readSync(fd, HEAPU8, addr, size, pos)` 实现即可);
  - `$libmupdf_stm_seek` 支持 whence 0/1/2,`handle.fileSize()` 提供文件长度;`handle.close()` 收尾。
- PDF 解析本身就是随机访问(尾部 xref 指哪读哪),结构化文本提取**不解码图片** → 常驻内存 = 当前页工作集(MB 级),与文件大小解耦。**与安卓原生按路径打开是同一内存模型**,逐页循环两端本来就同构。
- **于是"上限设 100MB 还是 1GB"的问题整个溶解:不再按文件大小设上限**。仅存物理天花板 wasm32 4GB 工作集(文字提取摸不到)+ 提取产出 100MB 上限(与纯文本同理,保留)。
- 实施时两个实证探针(按惯例用探针说话,不拍脑袋):
  1. 真实大 PDF(几百 MB 扫描件)验证峰值内存为工作集量级;
  2. 确认打开路径无隐藏"整流吞入"(理论上无,xref 随机访问是 mupdf 基本盘)。

### 2.3 子进程提取(角色:工程卫生,非内存妥协)
- 单 exe 自我 spawn 提取模式(env 标记),提取完写旁车即退出。价值:崩溃隔离(坏 PDF 炸不到主服务)、超时可杀、**wasm 堆只涨不缩**的特性随进程退出归零(现状:主进程提取过 90MB PDF 后那块堆永久占着)、逐页进度汇报通道(stdout)恰为方案②进度圆圈的数据源。
- 上传接口改为**落盘即返回**,提取全程后台;提取完成前发送走既有 fallbackDocumentText 降级,下轮自动带全文(机制已存在,上传路径接上而已)。

## 三、实施清单(五项,均已与用户对齐)

### ① PDF 流式提取 + 子进程 + 上传即时返回
- FD-backed StreamHandle(readSync 直读 HEAPU8)替换 readFileSync+buffer 打开;删除 `MAX_PDF_EXTRACT_BYTES` 文件级上限;保留提取产出上限(100MB,常量语义改名以自证);
- 提取挪入一次性子进程(自我 spawn + env 标记 + 超时杀 + stdout 逐页进度协议);
- 上传接口落盘即返回,提取后台化(接上既有 ensureExtractedTextAsync/兜底机制);
- accept 清单清理:去掉后端无解析器的 legacy Office(.doc/.xls/.ppt;.xlsx 同查);
- 探针实证:大 PDF 峰值内存 + 无整流吞入。

### ② 上传/解析确定性进度圆圈(用户明确要求:能看到进度的分段圆环,非转圈动画)
- 传输段:前端 XHR `upload.onprogress` 驱动 0→100%(fetch 不支持上传进度,用 XHR);chip 在点选后**立刻**以进度态出现(现状传完才出现,大文件期间无任何反馈,正是"以为应用坏了"的来源);
- 解析段:子进程逐页汇报 页数/总页数 → 主进程内存记录 → 前端轮询提取状态端点(上传响应携带初始状态);
- chip 状态机:上传中(环形%)→ 解析中(环形%)→ 完成(正常样式)/ 失败(可悬停提示角标,如"文件过大未提取全文"),**绝不静默**;
- 发送永不被解析段阻塞(降级机制见①)。

### ③ 粘贴转文件:PC 端固定开 + 阈值 5000(用户拍板)
- **不加 UI 开关;不读设置;不听安卓备份**——chat-input 直接用常量(开 + 5000 字符);
- `displaySetting.pasteLongTextAsFile/pasteLongTextThreshold` 字段继续原样存储并随备份透传(安卓端自用),PC 仅不消费 → 无迁移、无强刷、与安卓零打架(此前讨论过的存量迁移方案随之作废,不需要了)。

### ④ 超上下文报错人话化(用户拍板文案,不做花活)
- 识别三家 provider 的上下文超限错误(OpenAI `context_length_exceeded`/"maximum context length";Claude "prompt is too long";Gemini token 超限 INVALID_ARGUMENT),映射为固定文案:**"超出模型最大上下文窗口,建议压缩对话或切换窗口更大的模型"**;其余错误照旧。

### ⑤ 上传收尾 bug(✅ 已修,2026-07-29,未提交)
- 症状:上传 txt/csv 等报 "Cannot set properties of null (setting 'value')"(**上传实际已成功**,炸在收尾);
- 根因:chat-input.tsx `handleUploadInputChange` 在 `await` 后用 `event.currentTarget.value = ""`,React 的 currentTarget 仅同步分发阶段有值,异步恢复后为 null;文档与图片两个隐藏 input 共用此 handler,**所有经"+"菜单的上传都会触发**;粘贴/拖拽路径无此模式;
- 修复:await 前同步抓住 input 元素再清空(已改,web-ui tsc 干净);全仓扫描确认同类模式仅此一处;老 bug,非专题3引入;需进下一个安装包才能在 test4 上生效。

## 七、实施记录(2026-07-29 完成,全五项落地)

### 架构落点
- **提取全面子进程化**(超出原计划):不只 PDF,所有格式的全文提取都在用完即弃的子进程里跑
  (`files/extraction.ts`)。主进程从此不加载 mupdf wasm——wasm 堆只涨不缩的问题连根拔除;
  崩溃隔离、卡死可杀(5 分钟无进度停滞判死,逐页有进展的万页大书不会被误杀)、并发上限 2 排队。
- **单 exe 自孵化**:子进程命令 = `[process.execPath, ...process.argv.slice(1)]` + 环境变量
  `RIKKAHUB_EXTRACT_WORKER=1`;server.ts 在数据目录锁/端口绑定之前拐进 worker 分支。dev
  (`bun server.ts`)与编译单 exe 同一套代码。
- **PDF fz_stream 流式打开**(`files/index.ts extractPdfText`):`new mupdf.Stream({fileSize,
  read,close})`,read 回调 = `readSync(fd, wasm堆窗口, ...)`,内存 = 解析工作集。输入大小上限
  取消(`MAX_PDF_EXTRACT_BYTES` 删除);保留纯文本 100MB(JS 堆保险)与提取产出 100M 字符上限。
- **上传即时返回**:`files/upload` 字节落盘即返回(实测 40 页 PDF 16ms),响应带
  `extraction: "pending"|"none"`;新端点 `GET files/:id/extraction` 报 `{status, done, total}`,
  重启后旁车缺失时轮询本身自愈重启提取。DTO:`extractedTextLength` 退役,新增 `ExtractionStatusDto`。
- **registry 语义**(接替 in-flight 去重 + R4-4 负缓存):pending/done/empty/failed,empty 与
  failed 本次运行不重试(防"必崩文件"无限重生),重启/重传即重试。

### 前端
- 上传阶段:`api.postMultipartWithProgress`(XHR upload.onprogress,鉴权/错误语义与 ky 对齐,
  timeout=0),百分比进 store(`uploadProgress`)驱动输入框上传 chip 的确定性进度圆圈。
- 解析阶段:文档 chip 内 `ExtractionBadge` 每 600ms 轮询直到终态;PDF 画逐页百分比圆环,
  其他格式不定圈;failed/empty 显示可悬停警示角标;done/none 恢复普通 chip。发送不被提取
  阻塞(未完成走 fallbackDocumentText 降级,3-4 机制不变)。
- 粘贴转文件:chat-input 固定 `PASTE_LONG_TEXT_THRESHOLD = 5000` 且恒开,不再读
  `displaySetting.pasteLongTextAsFile/Threshold`(安卓备份的值不影响 PC;字段照常存储透传)。
- accept 清理:`.doc/.xls/.ppt` 与 **.xlsx**(同样从无解析器)一并移除,MIME 白名单同步收敛。
- ⑤ currentTarget bug 修复一并提交。

### ④ 报错映射
