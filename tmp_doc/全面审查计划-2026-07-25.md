# 重构收官·全面系统审查计划(2026-07-25)

## 审查立场与方法

- **视角**:假装第一次接触本项目,不以《项目重构方案.md》的叙事为前提,按成熟商业应用的标准冷读代码。
- **方法**:审查者亲自读代码,不使用子 agent。每阶段结束把发现写入《全面审查发现-2026-07-25.md》并 commit,然后由用户 compact 一次,再进入下一阶段。
- **评级**:P0=会造成数据丢失/崩溃/功能不可用,发布阻断;P1=明显 bug 或体验缺陷,应尽快修;P2=可维护性/健壮性隐患,择机修;P3=风格与优化建议。
- **每阶段固定动作**:①通读该域全部源码;②对照本阶段 corner case 清单逐条核对;③抽查与相邻域的边界契约;④发现即记录,不当场修(除非一行级、零风险)。
- **未来视角**:评估时兼顾路线图——多标签页 → 前端 UI/UX 重做 → 大文件流式上传+逐页解析 → 工作区/Agent 化。凡是会阻碍这四步的设计都要点名。

## 项目体量基线(2026-07-25 实测)

- pc-server 约 25.9k 行 / 18 个域;最大文件 inference-engine/providers.ts(1641)、search/index.ts(1269)、message-builder.ts(1042)、backup/import.ts(913)。
- web-ui/app 约 35.3k 行 / 165 个文件;最大 routes/conversations.tsx(2026)、settings/extensions.tsx(1949)、settings/providers.tsx(1393)、conversation-sidebar.tsx(1327)。
- 部署三形态:Tauri(Windows)、Linux 裸二进制、Docker;数据目录 pc-data/;与 Android APP 2.4.2 互备。

## 阶段划分与进度

### [x] 阶段0 全景与架构地图(本轮)
范围:目录结构、server.ts 入口与启动顺序、模块依赖方向(是否分层清晰、有无循环依赖)、全局单例与可变共享状态盘点、体量热点。
Corner cases:启动失败的半初始化状态;模块间通过全局 state 隐式耦合;import 副作用;foundation 反向依赖上层。

### [x] 阶段1 foundation + persistence + app-config
范围:foundation/types 数据契约、utils;persistence 的 state.json 读写/原子性/迁移链(appliedMigrations);app-config 配置来源与优先级。
Corner cases:并发写 state.json;写一半崩溃(断电/kill)的恢复;迁移在老数据各版本上的幂等性;字段增删对旧 state 的容错;超大 state(几千会话/几 GB 文件表)的性能;时区/时间戳格式;Windows 路径分隔符。

### [x] 阶段2 conversations + assistants 域
范围:SQLite 活库 schema 与索引、working set/checkout-release 生命周期、脏页节流落库、orchestrator 事件流、auxiliary(标题/建议)、assistants。
Corner cases:同一会话并发 generate;checkout 后进程崩溃的锁泄漏;删除正在生成的会话;分支(select_index)边界;truncateIndex 与消息编辑交互;SQLite busy/locked;WAL 文件迁移;会话数 5k+ 的列表性能;消息 JSON 超大(base64 图片)时的读写。

### [x] 阶段3 inference-engine
范围:providers.ts(各上游适配)、message-builder、流式事件协议、abort/超时、错误分类、token 统计、图片/工具调用往返。
Corner cases:上游断流/半截 JSON/keep-alive 超时;abort 后迟到的 chunk;工具调用循环上限;多模态消息在各 provider 的降级;reasoning 与 text 交错;上游 4xx/5xx 的用户可读错误;费用/用量统计漂移;并发多请求的资源隔离。

### [x] 阶段4 api 层 + server.ts + 通信协议
范围:全部 handler、路由注册、SSE 通道、请求体限制、错误响应一致性、静态资源服务、认证/局域网暴露面。
Corner cases:路径穿越(文件下载/上传名);超大 body;SSE 断连重连与事件丢失;慢客户端背压;并发 slot 上限(历史顽疾);JSON 解析失败的响应;跨形态(Tauri localhost vs Docker 0.0.0.0)的安全差异;端口冲突。

### [x] 阶段5 backup 域 + files 域(刚重构,重点)
范围:export/import/storage/file-refs 全量;files/index.ts 附件生命周期;三通路(PC→PC、PC→APP、APP→PC)契约;WebDAV(若有)。
Corner cases:零会话/零附件/纯设置备份;超大附件与 zip 大小;文件名冲突/非法字符/中文名;备份中途磁盘满;导入损坏 zip/截断 zip;v1.0.5 老备份;APP 新旧版本 zip;重复导入幂等;导入自己刚导出的 zip;pc_conversations.db 与 rikka_hub.db 不一致时的裁决;去重迁移在真实脏数据上的安全性。

### [x] 阶段6 外围域:tools / search / media / memory / model-providers / updates / observability
范围:各域完整通读。
Corner cases:工具执行超时/异常输出注入;search 各引擎失效降级;ASR/TTS 大文件与并发;memory 库损坏;provider 健康检查误报;更新检查网络失败;错误上报通道自身出错。

### [ ] 阶段7 web-ui 前端
范围:stores 状态管理、services(API 客户端/SSE 消费)、routes/conversations.tsx、chat-input、chat-message、settings 全家、hooks、i18n。
Corner cases:SSE 中断后的 UI 状态;发送中切换会话/助手;乐观更新与服务器回包冲突;长会话渲染性能;剪贴板粘贴大图;移动端/窄窗口;错误 toast 的可理解性;竞态的详情轮询;多标签页(路线图)对全局 store 的冲击。

### [ ] 阶段8 部署三形态 + 老用户迁移
范围:Dockerfile、docker-compose(若有)、Tauri 配置、构建脚本、pc-data 目录布局、版本升级路径(老 state → 新迁移链)。
Corner cases:Docker 卷权限/UID;Linux 二进制无写权限目录;Tauri 升级时数据目录变更;从重构前最后一个发布版直升本版的完整迁移演练;降级(用户回滚旧版)后数据是否被新格式毒化;首次启动空数据。

### [ ] 阶段9 横切汇总与终审报告
范围:日志与可观测性一致性、内存/性能热点复盘、测试与 smoke 覆盖缺口、路线图四步的架构就绪度评估、全部发现汇总分级、修复批次建议。
